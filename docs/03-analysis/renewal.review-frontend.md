## 지적 사항 — 위험·우선순위 순

### 1. [심각도 HIGH] app/(personal-home)/signup/complete/page.tsx:190 — 최초 조회 실패가 영구 로딩에 가려짐

- **문제:** `onboarding.loading || !onboarding.state`를 오류 분기(197행)보다 먼저 평가한다. 최초 GET이 429/503/네트워크 오류로 실패하면 기존 훅은 `loading=false`, `state=null`, `error`를 반환하므로 로딩 패널에서 계속 반환한다. 오류 메시지와 재시도 버튼에 도달하지 못한다. 이번에 추가된 온보딩 분기의 회귀다.
- **근거/재현:** 실제 페이지를 메모리에서 변환하고 세션·온보딩 훅을 대체한 React 서버 렌더로 위 세 실패 입력을 실행했다. 모두 `가입 상태를 확인하고 있습니다…`만 출력했으며 `ErrorPanel`은 없었다. 훅의 반환 동작은 `signup/hooks/useOnboardingStatus.ts:102` 이후 실패 처리와 대조했다.
- **수정 제안:** 재인증 → 오류 → 로딩 → 유효 상태 순서로 분기한다. 로딩이 끝났는데 상태도 오류도 없는 경우도 복구 가능한 오류로 처리한다. 최초 요청 실패 후 재시도로 정상 폼에 도달하는 시나리오를 검증한다.
- **설계/우선순위:** §3.1·§4.2 F-3/F-5, AC-06. **P0: 배포 전.**

### 2. [심각도 HIGH] app/(personal-home)/signup/complete/components/BusinessInfoForm.tsx:119 — 세션 갱신이 접수 성공 상태를 가진 폼을 제거함

- **문제:** POST 성공 후 `await update()`를 실행한 다음 자식 로컬 상태인 `isReceived`를 설정한다. 설치된 NextAuth의 `update()`는 `status="loading"`으로 전환한다(`node_modules/next-auth/src/react.tsx:515`). 상위 `complete/page.tsx:123`은 이때 폼 대신 로딩 트리를 반환하므로 기존 폼이 언마운트되고 입력값·접수 상태를 잃는다. 이후 `setIsReceived(true)`는 제거된 인스턴스에 적용된다. 새 온보딩 GET이 pending을 반환하면 상위 118행이 자동 이동시켜, 새로 만든 접수 안내와 사용자의 명시적 이어가기 절차를 건너뛴다. GET이 지연/실패하면 접수가 됐는데도 빈 폼 또는 조회 실패 흐름으로 복귀할 수 있다.
- **근거/재현:** NextAuth 구현, 상위 조건부 반환, 자식 상태 소유 관계를 정적으로 추적했다. 실제 브라우저의 요청 지연 재현은 수행하지 않았다. 이전에도 세션 갱신 시 폼 수명 문제가 있었지만, 이번 변경은 타이머 이동을 제거하고 로컬 접수 패널에 의존하므로 정상 성공 흐름의 인수 기준을 만족하지 못한다.
- **수정 제안:** 최초 세션 확인과 이미 인증된 상태의 갱신을 구별해 폼을 유지하거나, 접수 결과를 안정적으로 유지되는 상위 상태/가입 흐름 훅으로 올린다. POST 성공을 먼저 보존하고 세션 갱신 실패를 접수 실패와 분리한다. 접수 안내를 표시 중인 동안 상위 pending 자동 이동도 억제한다.
- **설계/우선순위:** §3.2·§4.2 F-2, 기획 TR-01/AC-02. **P0: 배포 전.**

### 3. [심각도 MED] app/(personal-home)/signup/business/steps/Step2Verify.tsx:48 — 수동 상태 확인 실패와 세션 만료를 숨김

- **문제:** 사용자가 누르는 “상태 다시 확인”까지 `refresh({ background: true })`를 사용한다. 기존 `useOnboardingStatus.ts:102`의 background 실패 분기는 401/429/503/네트워크 오류를 모두 무시하고 기존 pending을 유지한다. 버튼의 로딩만 끝나므로 사용자는 서버에서 여전히 pending임을 확인한 것과 조회 자체가 실패한 것을 구분할 수 없다. 401에서도 재로그인 안내가 나오지 않는다.
- **수정 제안:** 수동 확인은 오류·재인증을 노출하는 갱신으로 처리한다. 화면을 유지해야 한다면 refresh 결과를 훅에서 반환해 pending 패널 안에 실패/재인증 상태를 표시한다. 자동 포커스 갱신도 마지막 성공 시각과 실패 상태를 구분한다.
- **설계/우선순위:** §3.1·§4.2 F-3, AC-06. **P1.**

### 4. [심각도 MED] app/(personal-home)/renewal/_shared/signup-stage.ts:63 — 서버 접근 stage를 가입정보·플랜 선택 완료 사실로 오해함

- **문제:** 개인은 `stage !== "role"`이면 세부유형 저장 완료, `stage === "complete" || stage === "pay"`이면 명시적 플랜 선택 완료로 취급한다. 그러나 `lib/member-subscription/onboarding.ts:31`은 신규 기본 PERSONAL도 세부유형 선택 여부와 무관하게 complete로 반환한다. 승인된 임대도 무료 선택 전 complete이며, 부동산/기업은 승인만 받아도 플랜·기간 선택 전 pay다. 응답에 없는 사용자 선택 사실을 stage에서 만들어 내고 있다.
- **근거/재현:** 실제 순수 함수를 실행하면 PERSONAL/none/complete, RENTAL_BIZ/verified/complete, BUSINESS/verified/pay 모두 `completed=[1,2,3,4]`를 반환한다. 플랜 화면에서는 현재 단계의 체크를 숨기지만 다음 연결선을 이미 녹색으로 표시하고, 다른 단계에서는 플랜 완료 체크도 노출한다(`RenewalStageBar.tsx:84,108`).
- **수정 제안:** 서버의 앱 접근 가능 판정과 사용자 선택 사실을 분리한다. 명시적 선택 이벤트나 검증된 주문/선택 결과로 확인되지 않은 단계는 완료 체크를 유보한다. 현행 온보딩 응답만으로 PERSONAL 세부유형 저장 여부를 확정할 수 없다는 한계도 모델에 반영한다. 응답 필드나 서버 계약을 임의로 확장하지 않는다.
- **설계/우선순위:** §1.4·§2.4·§4.2 F-4, TR-03. **P1.**

### 5. [심각도 MED] app/(personal-home)/signup/complete/components/BusinessInfoForm.tsx:73 — 입력 필드의 키보드 포커스 표시 제거

- **문제:** 새 인라인 스타일은 `outline: "none"`인데 기존 `focus:border-primary`/`focus:border-red-500`도 제거했다. 입력에 별도의 focus 클래스·이벤트·공용 대체 스타일이 없어 Tab 이동 시 현재 입력 위치를 시각적으로 식별하기 어렵다. 오류 입력에도 동일하게 적용된다.
- **수정 제안:** CSS의 `:focus-visible`로 충분히 구분되는 outline 또는 테두리/링을 제공한다. 필드 오류에는 고유 ID와 `aria-describedby`를 연결하고, 제출 검증 실패 시 첫 오류 입력으로 포커스를 옮겨 오류를 찾기 쉽게 한다. 실제 키보드 순회로 확인한다.
- **설계/우선순위:** §4.2 F-6 및 기획 §8.2 키보드·접근성 검증. **P1.**

### 6. [심각도 MED] app/(personal-home)/signup/hooks/useVisibilityRefresh.ts:38 — 포커스 갱신과 수동 갱신이 같은 요청을 중복 실행

- **문제:** `lastRef`는 이 훅의 자동 이벤트만 제한한다. `Step2Verify.tsx:46`의 수동 갱신과 진행 중 요청 상태를 공유하지 않으므로 수동 조회 중 포커스/탭 복귀가 발생하면 같은 GET을 다시 실행한다. 10초 넘게 지연되는 요청도 다음 복귀 때 추가된다. 기존 `useOnboardingStatus`는 요청 세대로 늦은 응답을 버릴 뿐 요청을 합치거나 취소하지 않는다. 실패 시 고정 간격만 적용되고 429/지속 장애에 대한 백오프도 없다.
- **근거/재현:** 실제 훅을 메모리에서 변환해 effect/listener와 시간을 대체했다. 수동 요청 1개가 미완료인 상태에서 focus와 visibilitychange를 호출하면 총 2회, 10초 후 focus를 호출하면 총 3회가 됐다. 같은 시점의 focus+visibilitychange 자체는 throttle로 합쳐지며, 언마운트 리스너 정리는 정상임을 확인했다.
- **수정 제안:** 요청을 소유한 온보딩 훅에서 in-flight Promise를 공유하고 수동·자동 갱신에 공통 제한을 적용한다. 실패 결과에 따라 백오프하고, 재시도·언마운트 정책을 명시한다. 이벤트 훅에서 중복 상태를 따로 복제하지 않는다.
- **설계/우선순위:** §5.1 성능 및 기획 §5.1 읽기 제한·백오프, 플랫폼 중복 요청 금지. **P1.**

### 7. [심각도 MED] app/(personal-home)/signup/complete/page.tsx:83 — 페이지와 폼에 API·상태·업무 흐름이 계속 혼재

- **문제:** 페이지가 `runPersonalSetup`에서 직접 fetch·중복 실행 잠금·오류 상태·다음 단계 라우팅을 수행한다. `BusinessInfoForm.tsx:93`도 검증·POST·세션 갱신·접수 상태를 UI와 함께 소유한다. 이는 설계 §1.1의 “프론트는 상태/로직 계층 훅만 호출” 및 플랫폼의 페이지 조합/단일 책임 규칙에 어긋난다. 직접 호출 구조는 기존부터 있었으며, 이번 수정으로 해소되지 않은 **기존 잔존 설계 위반**이다. HTTP 요청 필드가 잘못됐다는 지적은 아니다.

- **설계/우선순위:** §1.1·§5.1, 플랫폼 단일 책임·폴더 구조. **P1: 위 기능 수정과 함께.**
