# VESTRA 1등화 로드맵 — 구현 설계 (효율·안정 중심)

> 작성 2026-09-10. 목적: P0-3~P0-7을 **한꺼번에 안전하게** 진행하기 위한 실행 설계.
> 원칙(규칙 0): 로컬≠운영이 갈리는 것(키·env·백필·스키마)은 절대 다른 작업과 섞어 한 번에 올리지 않는다.
> 핵심 전략 = **배포 리스크 등급으로 그룹핑** → 안전한 것끼리 묶어 1회 배포, 위험한 것은 격리·순차.

---

## 1. 배포 리스크 그룹핑 (효율+안정의 뼈대)

| 그룹 | 성격 | 배포 방식 | 해당 항목 |
|---|---|---|---|
| **A. 순수 코드** | DB·env·백필 무관. 런타임 리스크 낮음 | **한 배치로 묶어 1회 배포** | RightsResult 리팩터(완료·미배포), P0-5(CI 게이트=개발타임), P0-6(V-Score 공표=읽기전용 표시) |
| **B. env 키 + 백필** | 키 분리 후 기존 해시 재계산 필요. **PII 키 사고와 동급 리스크** | **단독 격리 배포 + 백필 프로토콜** | P0-3(SEARCH_INDEX_KEY 실분리) |
| **C. 신규 공공데이터 연동** | 외부 API + (선택)캐시 테이블 | 커넥터는 A로, 캐시 테이블 필요 시 별도 스키마 단계 | P0-7(악성임대인·HUG·건축위반) |
| **D. 스키마/감사** | 기존 `AuditLog` 재사용 여부에 따라 갈림 | 재사용이면 A, 신규 컬럼/인덱스면 별도 | P0-4(PII 접근 감사) |

> 결론: **한 번에 올릴 수 있는 건 그룹 A뿐**이다. B(P0-3)는 절대 배치에 섞지 않는다.
> C·D는 "코드 부분"과 "스키마 부분"을 분리해 코드는 A에 태우고 스키마는 별도 승인 단계로 뺀다.

## 2. 항목별 설계

### P0-3 SEARCH_INDEX_KEY 실분리 — 🔴 그룹 B (단독)
- **현황**: `lib/crypto.ts` `getSearchKey()` = `SEARCH_INDEX_KEY || AUTH_SECRET`(폴백). 운영에 전용키 **미설정 추정 → 착수 시 운영 env 실확인**(규칙 0-2).
- **대상 해시 2개**: `AgentClient.clientEmailHash`(이메일 blind index, 평문 `clientEmail` 존재→재계산 가능), `TrainingData.rawTextHash`(원문 해시, `rawText`에서 재계산).
- **위험**: 키를 바꾸면 `hashForSearch` 출력이 달라져 **기존 행 조회·유니크(agentId,clientEmailHash) 불일치** 발생. env-set과 백필 사이 창(window)에서 이메일 중복체크·조회가 깨질 수 있음.
- **안정 설계(듀얼리드 전환)**:
  1. 운영 env `SEARCH_INDEX_KEY` 생성값을 **로컬·Vercel 전 환경 동일** 설정(sha 대조, 값 미노출).
  2. `hashForSearch`에 **전환기 듀얼 계산** 도입: 조회 시 신규키 해시 우선, 없으면 구키(AUTH_SECRET) 해시로 폴백 매칭. 쓰기는 신규키.
  3. 코드 배포(듀얼리드 포함) → **배포 후** 백필 스크립트로 두 컬럼 신규키 재계산(멱등·dry-run 기본·`--commit`).
  4. 백필 100% 확인 후 다음 배포에서 구키 폴백 경로 제거(신규키 단일화).
- **롤백**: 듀얼리드라 백필 미완/중단해도 조회 안 깨짐. env 되돌리면 구키로 복귀.
- **검증(규칙 0-1)**: 운영에서 실제 고객검색·중복체크·training 중복탐지 화면으로 확인.

### P0-4 PII 접근 감사 로그 + 이상탐지 — 그룹 D→가능하면 A
- **현황**: `AuditLog` 모델 **이미 존재**(userId·action·target·detail·ip·userAgent·createdAt + 인덱스 3). 신규 테이블 불필요.
- **설계**: PII 조회 hot path(`AgentClient` 목록/상세, `admin/users`, 등기원문 조회 등)에 `action="PII_ACCESS"` 기록을 **공용 헬퍼 `logPiiAccess(userId, target, meta)`** 로 심음. 이상탐지 = 윈도우당 조회수 임계 초과 시 `action="PII_ANOMALY"` + 알림.
- **효율**: 기존 스키마 재사용 → **신규 컬럼 없으면 그룹 A로 편입**(마이그레이션 0). 단 기록이 hot path 성능을 해치지 않게 **비동기·베스트에포트**(실패해도 본 요청 안 깸)로. 대량 기록 상한·인덱스(createdAt) 이미 있음.
- **주의**: 감사 로그 자체에 PII 평문 저장 금지(target=id, detail=집계치만). 규칙 0-5 수명주기: 로그 보존기간·정리(cron) 포함.

### P0-5 SAST + 의존성 스캔(SCA) CI — 그룹 A (개발타임)
- **현황**: `prebuild`가 `audit-api-auth.mjs` 1개만. 
- **설계**: `scripts/audit-security.mjs`(SAST 경량 규칙: 위험 패턴 grep 게이트 — eval·dangerouslySetInnerHTML 미검증·평문 시크릿·미인증 변이) + `npm audit --production` 파싱(SCA, high 이상 실패)을 prebuild 체인에 **AND 연결**. 
- **안정**: **런타임 0 리스크**(빌드타임만). 오탐 억제 위해 allowlist. P0-2 `audit:ai-quality`처럼 실호출 게이트는 prebuild 미연결(비용).

### P0-6 V-Score 적중률 공표 — 그룹 A (읽기전용)
- **현황**: 백테스트 r=0.687 등 성능수치 존재(특허 포트폴리오). 
- **설계**: 정적 성능 데이터(`lib/vscore-performance.ts` 상수 = 검증일자·표본·상관계수·방법론) + 공개 페이지/섹션(신뢰 배지). **계산 아닌 표시**라 런타임 리스크 0. 수치는 추정 금지, 실제 백테스트 결과만.

### P0-7 공공데이터 연계 확대 — 그룹 C
- **현황**: gov 커넥터 다수 존재. 악성임대인·HUG 사고이력·건축위반 커넥터는 **없음**.
- **설계**: 커넥터(`lib/*-api.ts` 패턴 동일: 캐시·에러핸들·타임아웃) 신규 + 위험도(`risk-scoring.ts`) 입력에 신호 추가. 
- **분리**: **커넥터·스코어링 코드 = 그룹 A**. 조회결과 캐시가 필요하면 **캐시 테이블은 별도 스키마 단계(그룹 C)** 로 승인 후. 우선 무캐시(온디맨드)로 A에 태우고 캐시는 후속.

---

## 3. 실행 순서 (권장)

1. **배치 1 (그룹 A, 1회 배포)**: RightsResult 리팩터(완료) + P0-5(CI) + P0-6(V-Score 공표) + P0-4(AuditLog 재사용 확정 시) + P0-7 커넥터(무캐시). → 테스트 배포 → 실화면 확인 → 승격.
2. **배치 2 (그룹 B, 단독)**: P0-3 SEARCH_INDEX_KEY. env 동일설정 → 듀얼리드 배포 → 백필 → 검증 → 폴백 제거.
3. **후속(그룹 C/D 스키마)**: P0-4 이상탐지 고도화·P0-7 캐시 테이블 등 스키마 필요분만 별도 승인.

## 4. 공통 리스크 통제 (규칙 0)
- env/키 작업은 **로컬·운영 sha 대조(값 미노출)** 후 진행.
- 백필은 **코드 배포 후·멱등·dry-run 기본·비확장 PrismaClient**(이중처리 방지).
- 각 배치 승격 전 **병렬 코드리뷰(적대적)** + 견고성 4문.
- 그룹 A라도 배포 전 `lint`·`test`·`build`·smoke 필수.
