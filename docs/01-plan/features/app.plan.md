## 1. 기능 개요

비회원 등기감시 신청 폼을 플랫폼에서 이미 사용하는 전화번호 표시, 다음/카카오 주소검색, 집합건물 동·호 입력 패턴에 맞춘다. 이름·전화번호와 등기부 PDF만 입력해도 주소와 집합건물 동·호가 자동 반영되도록 한다. 주소를 먼저 검색한 경우에는 기존 주소 일치 검증을 유지한다.

신청 단계는 **신청 입력 → PDF 분석·초안 확인 → 본인인증 OTP → 주문·결제 → 서버 결과 확인·완료**를 그대로 유지한다. 기존 다날 인증 분기도 보존한다. 새 주소검색 UI, 별도 인증 단계, 임의 주소 보정, 새로운 결제 흐름을 만들지 않는다.

### 1.1 범위

| --- | --- |

## 4. UX 요구사항

### 4.1 입력과 자동입력

1. 기존 필드 순서와 카드·단계 표시를 유지한다. 주소에는 “주소를 검색하거나 PDF 분석으로 자동 입력할 수 있습니다” 수준의 안내를 붙인다. 이름·전화는 여전히 분석 전 필수다. 여기서 “PDF만으로 분석”은 **주소 사전 입력 생략**을 뜻한다.
2. 전화 `onChange`에서 숫자만 추출한 뒤 `formatMobile`을 적용한다. 초기값·OTP 복원값도 동일하게 표시한다. 요청·DB 저장·신원 해시는 기존 `normalizeGuestPhone` 기준으로 일관되게 처리한다.
3. 주소 상태는 `AddressValue`로 관리하고 `AddressSearchField`에 전달한다. 검색 결과가 없는 PDF 추출값에 우편번호·도로명·지번을 추정해 넣지 않는다. 추출한 주소 종류가 명확하면 해당 필드에만 배치한다.
4. PDF 선택 자체는 분석 성공으로 간주하지 않는다. 기존 “등기부 분석하기” 요청 성공 시 주소와 동·호를 채우고 확인 영역에 같은 값을 표시한다. 새 draft 응답을 받은 이벤트에서 동기화하며 최초 `useState` 초기값에 의존하지 않는다.
5. 사용자가 주소를 먼저 선택했다면 PDF와 비교에 성공한 경우에만 자동입력 결과를 반영한다. 불일치는 기존 오류로 안내하고 기존 입력을 보존한다. 분석 도중에는 입력을 잠가 지연 응답이 새 입력을 덮어쓰지 못하게 한다.

### 4.2 집합건물과 수정

- `AGGREGATE_TYPES`의 세 유형과 `isAggregate` 조건부 노출·`dongHoMissing` 진행 차단 패턴을 따른다. PDF의 `다세대주택` 등은 기존 세 유형으로 명시 매핑한다. 검색 결과의 `isBuilding`과 PDF의 집합건물/전유부분 근거도 활용하며 단지명에 “아파트”가 있다는 이유만으로 판정하지 않는다.
- 동·호 UI는 공통 컴포넌트의 기존 필드를 재사용한다. 공통 `value.isBuilding`은 집합건물 판정 결과와 일치시킨다. 비집합건물에서는 동·호 필수 검증을 적용하지 않는다.
- `제101동 제15층 제1502호`는 `dong=101`, `ho=1502`로 분리한다. 행정동·지번·층을 동·호로 오인하지 않고, `동동`·`호호` 중복 접미사를 만들지 않는다.
- 성공한 초안은 기존대로 잠근다. 수정 가능성은 기존 “다시 입력” 경로로 제공한다. 클릭 시 기존 초안·주문 재개 참조·OTP·동의를 무효화하고 입력값과 선택 PDF는 가능한 범위에서 유지하여 재분석한다.
- PDF에서 동·호를 확정하지 못하면 임의 보완해 결제 가능한 초안을 만들지 않는다. 입력 또는 재업로드로 보완·재분석하도록 안내하되 서버가 PDF와의 정합성을 확인할 수 없는 값은 확정하지 않는다. 비숫자 동·호는 공통 필드가 숫자만 받으므로 잘라서 다른 호수로 만들지 않고 지원 불가 안내와 재확인 경로를 제공한다.

### 4.3 업로드 영역

- 카드 내부 가용 폭 기준 `width: 100%`, `box-sizing: border-box`를 적용한다. 부모 카드 최대 폭은 기존대로 유지한다. 공유 `.mDropZone` 전체를 바꿔 회원 폼까지 영향을 주기보다 비회원 범위 클래스를 우선한다.
- 파일명 줄바꿈·긴 파일명 넘침, 모바일 320/375px 및 데스크톱을 확인한다. 키보드 접근 가능한 버튼·파일 입력·선택 상태 표시·분석 중 비활성화를 유지한다.
- 드롭 시에도 파일 선택과 같은 파일 검증·단일 파일 정책을 사용한다. 기존 프로젝트 드롭 처리 패턴을 재사용하고 새로운 업로드 라이브러리는 도입하지 않는다.

## 5. 기술 요구사항

### 5.1 요청·응답 계약

대상 API는 기존 `POST /api/guest-monitoring/parse-pdf`다.

| 항목 | 계획 계약 |
| --- | --- |
| 필수 요청 | `file`, `guestName`, `guestPhone` 유지 |
| 선택 요청 | `address`: 기본 주소. 검색 선택 시 PDF 지번과 비교할 수 있도록 `jibunAddress || roadAddress`를 사용. 누락·빈 문자열·공백만 있는 경우를 모두 미제공으로 정규화 |
| 동·호 요청 | 선택 문자열 `dong`, `ho` 추가. 기본 주소와 함께 제출할 때만 허용. 길이·문자 검증과 중복 키 거부 적용 |
| 기존 호출 호환 | 기존 주소 문자열 제출 경로와 오류 계약 보존. 주소에 상세가 이미 포함된 입력도 회귀 확인 |
| 기존 응답 | `draftId`, `address`, 마스킹 고유번호·소유자, `extractionOk`, `draftExpiresAt` 유지 |
| 추가 응답 | `addressValue: AddressValue`, `propertyType: string \| null`을 제공하는 방향. 주소 필드에는 서버가 확인한 값만 포함 |
| 실패 응답 | 기존 `GuestApiError`와 비-2xx 계약 유지. 주소/동·호 추출 불완전은 `extraction_incomplete`, 사용자 입력과 불일치는 `address_mismatch` |

`addressValue`는 UI 복원용 데이터이며 서버 소유자·고유번호의 입력 경로가 아니다. 요청에 `ownerName`, `commUniqueNo`, 금액, 임의 `addressValue` 객체가 추가되면 기존처럼 거부한다. FormData 허용 목록·Zod strict 계약을 함께 수정한다. 비어 있지 않은 잘못된 주소를 미제공으로 묵살하지 않고 기존 길이·문자 검증으로 거절한다. 새 응답 필드는 우선 호환 가능한 추가로 적용하고 구 응답의 복원 처리도 고려한다.

### 5.2 주소 미제공 추출과 일치 검증

1. `createDraft`는 주소를 필수로 요구하지 않되 이름·전화 검증과 PDF 확장자·MIME·매직바이트·용량 검증을 그대로 수행한다.
2. `extractRegistryFields(text, inputAddress?)`로 선택 주소를 받는다. 기존 등기부 판별·갑구 존재·다중 고유번호 거부·고유번호·현재 유효 소유자 추출·공유/법인 등 모호한 소유자 거부를 보존한다.
3. `parseRegistry`의 표제부 주소·유형·전유부분 정보를 재사용한다. 부족한 구조화는 `lib/guest-monitoring/` 내부 순수 변환/추출 함수로 보완한다. 전유부분 표식 누락·동호가 다른 줄에 있는 실제 fixture도 확인한다. 소유자의 거주지나 대지권 다른 필지 주소를 감시 물건 주소로 사용하지 않고 접수번호의 `제○호`를 호수로 오인하지 않는다.
4. 주소 미제공이면 **사용자 주소와의 비교만** 생략한다. PDF 주소 추출 성공은 여전히 필수이며 실패 시 초안을 저장하지 않는다. 고유번호·소유자 검증 완화는 없다.
5. 주소 제공 시 기존 `normalizeAddress`를 이용한 정확한 동일성 검증을 유지한다. 부분 문자열·유사도 비교로 완화하지 않는다. 기본 주소와 동·호를 구조적으로 나누어 각각 비교하여 같은 단지의 다른 동·호는 반드시 거절한다.
6. 검색으로 얻은 도로명·지번 중 PDF 기준과 맞는 주소를 비교용으로 선택한다. 표시용 `composeAddress`의 도로명 우선 규칙을 서버 비교 규칙으로 오용하지 않는다. PDF나 기존 검색 결과에서 동일성 근거를 확보하지 못한 도로명/지번 변환은 임의 허용하지 않는다.
7. 저장용 `address`는 서버가 검증한 기본 주소와 동·호를 중복 없이 조합한다. 고유번호·소유자는 동일 PDF의 추출 결과로만 저장한다. 감시 어댑터의 `reqAddress`·고유번호·소유자 조합을 회귀 확인한다.

현재 DB는 암호화된 주소 문자열을 보유하고 동·호 전용 컬럼은 없다. 이번 기능은 기존 주소 컬럼과 응답 메타데이터로 처리하며 신규 스키마 변경을 전제하지 않는다. 추출 메타데이터를 DB create의 `...fields`에 그대로 펼쳐 존재하지 않는 컬럼을 쓰지 않도록 저장용 값과 응답용 값을 분리한다.

### 5.3 흐름·보안·멱등 보존

- `useGuestApply`의 `genRef`, reset·재분석·언마운트 시 오래된 응답 무시, `useGuestOtp`, `useGuestOrderFlow` 책임 분리를 유지한다.
- 수정 후 초안만 바꾸고 기존 OTP·주문 참조를 재사용하지 않는다. OTP 취소·재발송 실패로 폼이 재마운트될 때 이름·포맷된 전화·자동입력 주소·동·호가 복원되어야 한다.
- 인증 시작 전에 유효 초안·집합건물 필수값·동의를 확인한다. `extractionOk=false` 또는 검증 실패에서 인증·주문·결제로 진입하지 않는다.
- 세션·브라우저 바인딩·신원 해시, 초안 만료, 주문 멱등키, 동일 물건 중복 활성 방지, SDK 재진입 잠금, 401 재인증·결제 복구 정책을 보존한다.
- 결제 성공은 기존 서버 주문의 `paid && applied`만 근거로 삼는다. OTP 성공·SDK 반환만으로 완료 처리하지 않는다.
- 기존 `endpoint`, Origin 검증, 기능/암호화 게이트, IP 제한, `no-store`, 11MB 요청·10MB PDF·40페이지·텍스트 길이 제한, PDF 리소스 정리를 보존한다.
- 소유자·고유번호는 UI에서 계속 마스킹한다. PDF 원문·주소·전화·인증정보를 URL·브라우저 저장소·로그에 추가로 저장하지 않는다. 개인정보 암호화 경로는 기존대로 유지한다.

## 6. 테스트 계획 및 완료 기준

테스트 추가·실행은 후속 구현 단계의 필수 작업이다. 현재 기본 Vitest 설정은 `__tests__/**/*.test.ts`, 별도 비회원 설정은 `lib/guest-monitoring/tests/**/*.test.ts`를 수집하며 모두 Node 환경이다. DOM 테스트 도구는 현재 의존성에 없으므로 UI 테스트가 이미 가능한 것으로 간주하지 않는다. 순수 함수·서버 경로는 Vitest로 검증하고 실제 렌더·이벤트·폭·포커스는 브라우저 검증을 병행한다. UI 자동화 도구 추가가 필요하면 별도 영향 범위를 명시한다.

| 구분 | 필수 사례와 합격 기준 |
| --- | --- |
| 전화 포맷 단위 | 숫자 입력·하이픈 붙여넣기·문자 섞임·삭제·10/11자리·11자리 초과를 기존 `formatMobile` 동작으로 검증. 완성값 `010-0000-0000`, 서버 저장은 숫자 정규형, 하이픈 유무에 따른 신원 해시 동일 |
| 주소 없는 PDF 분석 | `extractRegistryFields` 주소 인자 생략, `createDraft` FormData 주소 키 생략/빈 값/공백 세 경우 성공. 이름·전화는 계속 필수. 추출 주소 없는 문서는 저장 0회 |
| 주소 자동입력 | 비동기 분석 성공 후 주소검색 필드·확인 영역·제출 상태가 같은 주소. 최초 빈 상태에서도 반영. 기존 사용자 주소 불일치 시 입력 보존 |

| 주소 정합성 | 동일 주소 정규화 성공, 도로명/지번 선택 기준 검증, 다른 기본 주소·같은 단지의 다른 동/호 거부, 행정동과 건물동 혼동 방지, 중복 접미사 방지 |

| 수정·경합·복원 | 다시 입력 시 초안·동의·OTP·재개 참조 무효화, 수정값 재검증, 지연 응답 무시, OTP 취소·재발송 실패 후 입력 복원 |

| 업로드 UI | 클릭·키보드·드롭 동일 검증, 파일 교체·긴 파일명·disabled, 모바일/데스크톱에서 다른 입력과 같은 좌우 경계와 100% 폭 |

후속 검증 명령은 `npm run test -- <추가 단위 테스트 경로>`, `npx vitest run --config lib/guest-monitoring/vitest.config.ts`, 변경 파일 lint, `npm run build`를 기본으로 한다. 격리 DB가 필요한 테스트는 기존 비회원 README 조건에 맞춰 실행하고 실제 외부 문자·결제 호출 없이 검증한다. 기존 `security.test.ts`의 주소 일치·추출 실패 사례를 보존·확장한다.

완료는 요구사항별 테스트 결과, 브라우저 UI 확인 결과, 500줄 점검, Codex 교차검수 결과가 모두 기록된 상태다. 이번 문서 작성에서는 테스트 통과나 기능 구현 완료를 주장하지 않는다.

## 8. Codex 교차검수

기획 단계에서 별도 Codex 검수자가 기존 코드와 요구사항을 독립적으로 대조했고, 아래 쟁점을 문서에 반영했다. 검수 초점은 공통 UX 재사용, 주소 선택 입력화의 전 구간 반영, 동·호와 물건 식별 정합성, 초안 무효화, 기존 인증·결제 보호 장치 보존이다. 실제 코드 구현 검수와 테스트 통과 판정은 후속 구현 단계에서 다시 수행한다.

| 사전 검수 쟁점 | 문서 반영 사항 |
| --- | --- |
| 주소 선택 입력화가 프론트에만 반영될 위험 | 폼·훅·API 클라이언트·스키마·FormData·추출 함수까지 변경 범위 명시 |
| 새 draft가 입력 필드 초기값에 반영되지 않음 | 응답 이벤트 기반 동기화와 OTP 복원 기준 명시 |
| 공통 주소 컴포넌트에 동·호가 이미 존재 | UI 중복 금지, Jeonse의 판정·필수 검증 패턴만 결합 |
| 도로명 우선 조합과 PDF 지번 비교 충돌 | 표시/비교 주소 구분, 정확 일치와 동호 개별 검증 유지 |
| 자동입력값을 수정하면서 과거 초안 결제 가능 | 기존 다시 입력·재분석과 초안·OTP·동의·주문 참조 무효화 유지 |
| 추출 메타데이터 DB 전개와 감시 조회 영향 | 저장용/응답용 데이터 분리, 최종 주소·고유번호·소유자 회귀 검증 |

후속 구현 교차검수에서는 실제 diff·추가 테스트·검증 로그를 대조하고, 고유번호/소유자 신뢰 경계 변경이나 미검증 동·호 허용이 발견되면 완료 판정을 보류한다.
