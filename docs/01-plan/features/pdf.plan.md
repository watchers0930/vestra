> 프로젝트: VESTRA

## 1. 기능 개요

비회원 등기감시의 물건 입력을 등기부등본 PDF 하나로 통합한다. 신청자 이름·전화번호는 유지하되 별도 주소 입력과 입력 주소/PDF 주소 일치검증을 제거한다. 서버가 PDF에서 주소·집합건물 동/호수·부동산 고유번호·소유자를 추출해 화면에 자동입력한다. 사용자는 분석 결과를 확인하고 역할을 선택한 뒤 동의, SMS OTP 인증, 결제, 감시 시작 순서로 진행한다.

역할은 `owner`(소유자/내 물건)와 `tenant`(임차인/세입자) 두 가지다. 소유자는 인증에 사용한 `guestName`과 PDF에서 추출한 소유자명을 서버에서 정규화 비교한다. 불일치하면 **“본인 소유 물건이 아닙니다”**로 거부하며 결제를 진행하지 않는다. 임차인은 소유자명 대조를 생략한다. 감시 변동 안내도 소유자에게는 명의도용·무단처분 위험, 임차인에게는 보증금 위험을 중심으로 제공한다.

### 1.1 확정 사용자 흐름

| 순서 | 화면/처리 | 다음 단계 조건 |
| --- | --- | --- |
| ① 입력 | 이름, 전화번호, 등기부 PDF 업로드. 주소 입력란 없음 | 필수값·PDF 유효성 충족 |
| ② 분석 | 서버 추출 → 주소·동/호수·고유번호·소유자 자동입력 및 결과 확인/수정 UI | 단일 물건·필수 추출값 확보, 수정값 서버 처리 완료 |
| ③ 역할 | “소유자(내 물건)” / “임차인(세입자)” 중 명시적 선택 | 허용된 역할 1개 선택 |
| ④ 동의·인증 | 필수 동의 → 기존 SMS OTP. 소유자만 인증 성공 후 이름 대조 | 인증 성공 및 역할별 검증 통과 |
| ⑤ 결제 | 서버가 정한 10,000원 결제 | 서버 승인 검증 성공 |
| ⑥ 감시 시작 | 결제 주문 적용 후 감시 활성화·완료 표시 | 서버 상태 `paid` 및 `applied` 확인 |

“PDF-only”는 **물건 식별 입력**에 대한 요구다. 이름·전화번호·역할·동의·OTP 입력은 유지한다. 분석 전 주소 수동입력 및 주소 일치검증을 재도입하지 않는다. 분석 후 추출값 수정은 요구사항에 포함하며, 원본 신뢰·PII와 충돌하는 부분은 §6의 설계 결정 항목으로 명시한다.

## 4. 기술 요구사항

### 4.1 PDF-only 서버 분석

- `extractRegistryFields(text)`로 단순화한다. 호환 때문에 두 번째 인자를 일시 유지하더라도 신규 비회원 경로에서는 전달하지 않고 매칭검증을 실행하지 않는다. 최종 목표는 해당 경로의 주소 비교 의존 제거다.
- `createDraft`의 허용 키와 데이터 변환에서 `address` 제거, `applicantSchema.address` 제거, `guestApi.parsePdf`·`ApplyInput`·훅 검사에서 address 제거. 잔존 address 요청은 strict 검증으로 거부하며 입력 경로를 몰래 유지하지 않는다.
- 반환 계약은 서버 추출 `address`, `unitNumber`(기존 파서 표현 활용), `commUniqueNo`, `ownerName`을 기준으로 한다. UI에서 동/호수를 별도 항목으로 표시하며, 필요하면 buildingDong/unitHo를 파생한다. 외부 응답의 고유번호·이름은 §6의 PII 정책을 따른다.
- 주소는 물건 표제부에서만 취한다. 소유자 주소·대지권 토지 주소·다른 전유부분을 물건 주소로 오인하지 않는다. 동/호수 역시 해당 집합건물 전유부분에 결합한다.
- 집합건물에서 필수 호수를 특정할 수 없으면 재업로드 안내로 중단한다. 원문에 동 구분이 없는 건물은 동을 만들어내지 않는다. 비집합건물은 동/호수 “해당 없음”을 허용한다.
- 기존 10MB, PDF MIME/확장자/magic bytes, 1~40쪽, 추출 텍스트 길이, 등기부 판정·갑구·단일 고유번호·유효 소유자 검증과 PDF 리소스 정리를 유지한다. 공동/법인/마스킹 등 기존 지원 제외 조건은 유지한다.
- 추출 실패 시 수동 주소로 우회하지 않는다. 올바른 PDF 재업로드로 복구한다. 불필요해진 `address_mismatch` 메시지/호출을 비회원 경로에서 정리하되 공용 유틸 참조 여부를 먼저 확인한다.

### 4.2 역할 수집·저장 계약

분석 후 역할을 선택하므로 `parse-pdf`에는 역할을 필수로 요구하지 않는다. **권장안은 신청 인증 시작 요청에 역할을 추가**하고 서버에서 초안에 저장하는 방식이다. 역할 선택/확인값 저장은 OTP를 발송하기 전에 완료한다.

| 단계 | 요청/처리 계약 |
| --- | --- |
| parse-pdf | multipart `file`, `guestName`, `guestPhone`만. 서버가 초안과 추출 기준값 생성 |
| 분석 결과 확인 | 추출값 편집은 별도 서버 확인 계약으로 처리. 기존 parse-pdf에 임의 ownerName/고유번호를 허용하지 않음 |
| identity/start apply | 기존 이름·전화·draftId에 `role: 'owner' \| 'tenant'` 추가. 신청에서만 필수, 조회/연장에는 요구하지 않음 |
| 서버 역할 저장 | 초안 만료·상태, 신청 신원 해시, 기존 브라우저 결합 정책을 검증. 동일 신원 잠금 안에서 저장·인증 시작 |
| OTP 성공 → order | 서버 DB의 확정 role·추출 ownerName·guestName으로 판정. 주문 요청에서 역할/소유자를 덮어쓰지 않음 |
| 최초 활성화 | 서버에 저장한 role/검증 조건 재확인. 신규 초안의 null/알 수 없는 역할은 차단 |
| 재발송/복구/연장 | 동일 역할 유지. 이미 인증 중이거나 주문이 있는 초안은 역할·물건값 변경 금지 |

공유 타입에 `GuestMonitoringRole = 'owner' | 'tenant'`를 추가한다. 신청 인증 DTO·strict schema·훅에서 동일 타입을 사용한다. 생략/임의 문자열/배열/중복키를 허용하지 않고 브라우저 라디오의 값만 믿지 않는다. 역할은 권한을 확대하는 플래그가 아니며 tenant도 기존 인증·동의·결제·조회 권한 검증을 통과해야 한다.

### 4.3 Prisma와 기존 데이터

- 후속 구현에서 `GuestMonitoring`에 **`role String? // owner | tenant, 미선택 초안/기존 레코드는 null`** 추가를 권장한다. String 값은 서버 enum으로 제한한다. 분석 직후 역할 미선택 상태와 기존 레코드를 표현하려는 선택이다.
- owner/tenant 기본값을 자동 부여하지 않는다. 기존 신청자의 역할을 추정해 소유자 검증 완료로 간주해서는 안 된다. 신규 신청은 주문 전에 반드시 유효한 role을 가져야 한다.
- 기존 active/expired의 null 역할은 서비스·조회·기존 주문 복구를 보존하고 중립 알림을 사용한다. 이미 결제된 기존 건을 새 조건으로 거부하지 않는다. 새 초안과 기존 건의 구분 기준 및 기존 pending 주문 처리 정책은 설계에서 명시한다.
- 이번 요구의 추가 컬럼은 role만이다. 동/호수는 기존 암호화 `address`에 주소와 함께 보존하고 응답에서는 `unitNumber`로 분리하는 방식을 우선 검토한다. Tilko `reqAddress`와 달력 주소 축약이 영향받으므로 호환 테스트를 필수로 한다. 별도 동/호수 컬럼이 필요하면 별도 범위로 제안한다.
- **운영 적용은 사용자가 별도 수동 ALTER한다.** 이 작업과 후속 기능 구현에서 운영 `prisma migrate*`, `prisma db push`, ALTER를 자동 실행하지 않는다. 운영 DB 접속·조회도 본 기획에 필요하지 않다.
- role을 조회하는 새 Prisma Client는 컬럼이 없는 DB에서 오류를 낼 수 있다. 테스트 DB 호환 검증 → 사용자의 운영 컬럼 추가 확인 → 새 코드 배포 순서로 분리한다. 기능 OFF만으로 모든 ORM 조회 오류가 차단된다고 가정하지 않는다.
- 운영 롤백은 역할 컬럼을 남겨 둔 채 이전 코드로 복귀하는 추가전용 방식을 기본으로 한다. 운영 적용 전 컬럼 null/default·기존 건 처리 기준을 사용자 수동 ALTER와 일치시킨다.

### 4.4 소유자명 대조

1. OTP 성공과 해당 draft의 인증 신원 결합을 먼저 확인한다. 이름은 새 주문 요청값 대신 인증에 결합된 초안의 `guestName`을 사용한다.
2. `role=owner`일 때만 서버 저장 PDF 추출 `ownerName`과 비교한다. 수정 UI에서 입력한 이름으로 PDF 원본 소유자를 덮어써 대조하지 않는다.
3. 비교 전용 함수에서 양쪽에 NFKC, 앞뒤 공백 제거, 내부 공백 제거를 적용한다. 예: ` 홍 길 동 `과 `홍길동`은 일치. 성명 일부·유사도·접두어만으로 승인하지 않는다. 지원하지 않는 이름/소유 형태는 기존처럼 중단한다.
4. 기존 `normalizeGuestName`/`guestIdentityHash`의 의미는 변경하지 않는다. 비교 편의를 위해 신원 HMAC까지 바꾸면 기존 조회·주문 복구가 끊어질 수 있다.
5. 불일치는 `GuestError('owner_name_mismatch', 403)`와 **“본인 소유 물건이 아닙니다”**로 통일한다. 응답/로그에 두 이름 원문을 포함하지 않는다. 결제 launch 데이터 생성·SDK 실행 전에 거부한다.
6. `tenant`는 비교만 생략한다. PDF의 ownerName은 감시 upstream 조회에 여전히 필요하다.
7. 주 검증 지점은 최초 `createOrder`이며, 신규 건의 미결제 existing/pending 주문 조기 반환보다 앞에서 검사한다. 진행 주문 재사용·콜백 활성화·복구에서도 우회되지 않도록 같은 서버 정책을 공유한다. 이미 적용된 주문의 멱등 반환과 기존 null 역할 건은 별도 호환 정책으로 보존한다.
8. 결제 승인 이후 활성화 방어 검증에서 예외가 발견되면 승인 증빙을 보존하고 기존 `needs_review` 정책에 맞춰 수동 확인 대상으로 남긴다. 단순 실패로 결제 사실을 유실시키거나 새 결제/자동 환불을 실행하지 않는다.

SMS OTP는 전화 수신 권한을 확인하며 입력 이름의 실명을 검증하지 않는다. 이 기획의 이름 일치는 **요청한 신청 조건**이며 소유권의 독립적 증명이 아니다. 기존 OTP 보증 수준·서비스 안내를 과장하지 않는다.

### 4.5 프론트와 상태 관리

- 최초 입력은 이름·전화·PDF 세 항목. 전화 onChange/초기 복원에 `lib/phone-format.ts`의 `formatMobile` 재사용, 서버는 기존 `normalizeGuestPhone`으로 정규화한다.
- 업로드 버튼은 비회원 로컬 class로 `width: 100%`, `box-sizing: border-box` 적용. 입력·주요 버튼과 좌우 경계 일치, 모바일 긴 파일명에도 넘침 없음. 파일 선택과 키보드 접근·disabled 동작 유지.
- 분석 완료 후 주소·동/호수·고유번호·소유자 확인/수정 UI를 표시하고 그 아래 역할 선택, 필수 동의, “본인인증 후 결제 (10,000원)”을 제공한다. 두 역할은 기본 선택 없이 동일한 비중으로 표시한다.
- 역할 선택은 접근 가능한 radio group 또는 동등한 키보드 조작을 제공한다. 분석/저장/인증 중 중복 제출을 막고 서버 오류를 `role=alert`로 표시한다.
- 추출값 수정·PDF 교체·신청 이름/전화 변경 시 기존 인증·동의·주문 진행 참조를 무효화한다. 이미 주문이 생겼다면 해당 초안을 수정하지 않고 기존 주문 확인 또는 새 신청으로 분기한다. 이전 비동기 응답의 세대 가드를 보존한다.
- OTP 취소·재발송·폼 재마운트 때 이름·전화·역할·확인 결과를 복원한다. 인증 중 role 교체 경합은 서버에서도 거부한다. 수정 가능한 정보의 원본/수정 상태를 구분한다.
- 기존 `input → ready → otp → ordering → paying → recovering → done` 흐름을 확장하되 주문 실행·복구 책임은 `useGuestOrderFlow`에 유지한다. 표시 단계는 PDF 분석·역할·인증·결제·완료를 이해할 수 있게 안내한다.
- 페이지/컴포넌트/훅은 파일당 500줄 이하를 유지한다. 추출 결과 패널·역할 선택·소유자 검증·알림 문구 생성은 책임별로 분리하고 대규모 무관 리팩터링은 하지 않는다.

### 4.6 결제·보안·PII 불변조건

- 인증 성공만으로 active 전환하지 않는다. 가격·통화·기간은 기존 서버 SSOT 사용. 결제 공급자의 서버 재조회로 승인 확인 후 주문을 적용한다.
- 신원 잠금, 멱등키, 미완료 주문 재사용, 중복 활성 방지, `needs_review`, 콜백 서명/nonce, 주문 `appliedAt`의 1회 적용을 유지한다. 역할을 바꿔 별도 중복 활성 물건을 만들 수 없다.
- 401은 재인증으로 처리하고 기존 주문/키 유지. 승인 가능성이 있는 결제는 새 SDK 실행 대신 상태 재조회·콜백 복구를 우선한다. OTP 취소·오류·소유자 불일치 상태에서는 결제 진입 금지.
- 기존 `endpoint`, Origin·rate limit·크기 제한·기능/암호화 키 게이트·세션 쿠키·브라우저 바인딩·no-store를 유지한다. 추출값 확인 API도 같은 경계를 사용한다. 인증 전 편집/재조회 API는 draftId만으로 허용하지 않고, 해당 업로드 브라우저에 결합한 단기 capability 등 소유 증거와 TTL을 검증한다. 인증 후 원문 조회는 동일 초안의 인증 세션으로 제한한다.
- 이름·전화·주소·소유자 암호화와 blind index 유지. 원본 PDF·추출 전문·OTP·민감 필드를 로그/URL/localStorage/sessionStorage에 저장하지 않는다. 기존 복구 저장소는 비민감 식별자만 유지한다.
- PDF 원본이나 고유번호/소유자 수정값을 브라우저 제출만으로 감시 원본으로 채택하지 않는다. 세부 수정 정책은 §6에서 확정한다.

### 4.7 역할별 알림

| 역할 | 확인된 변동에 사용할 핵심 문구 |
| --- | --- |
| owner | “내 물건에 무단 근저당/소유권이전 감지—명의도용 의심” |
| tenant | “임대인 물건 근저당/소유권이전/압류—보증금 위험” |
| 기존 null | 기존 중립 문구. 소유자/임차인으로 임의 분류하지 않음 |

- 위 문구는 요청된 역할별 경보 기준이다. 실제 템플릿에서는 확인된 사건 종류만 삽입한다. 사건 종류가 없거나 접수 단계이면 “등기신청 사건 감지—명의도용 여부를 확인해주세요” / “임대인 물건 등기신청 사건 감지—보증금 위험을 확인해주세요”처럼 단계에 맞춘 예비 경보를 사용한다.
- `hasSignal`만으로 근저당·소유권이전·압류 모두가 발생했다고 출력하지 않는다. precheck는 사건 신호이며, 최신 등기부 확정 변동과 구분한다. “무단” 여부도 독립적으로 입증되는 값이 아니므로 의심/확인 요청 맥락을 함께 제공한다.
- 역할과 정제된 사건 타입/단계를 받는 서버 메시지 빌더를 단일 소스로 둔다. `precheck-adapter` 저장 요약, `registrySignalSummary`, `calendar-dto.safeSummary/getCalendar` 재생성 결과에 같은 정책을 적용한다. `no_change/fetch_failed`를 위험 경보로 만들지 않는다.
- 현재 guest에 변동 SMS 큐가 없으므로 문구만 바꾸면 문자 알림이 완성된다고 간주하지 않는다. 화면/달력 알림과 외부 발송 경로를 구분해 검증한다. 외부 변동 SMS는 발송 생성·만료 확인·재시도·불명 결과 처리까지 설계해야 한다.
- 기존 outbox는 만료기간당 1회와 expired 조건에 묶여 있다. 변동 이벤트에는 동일 사건을 식별하는 중복방지 기준이 필요하다. `receiptNo` 등 안정된 사건 식별자 확보를 우선 검토하고, 반복 precheck마다 같은 경보를 발송하지 않는다.
- role 외 DB 컬럼 변경은 현재 범위가 아니다. 변동 발송의 이벤트 보존/유일키가 기존 구조로 안전하게 구현되지 않으면 별도 DB 설계로 분리해 범위를 확정한다. 만료 안내 문자·기존 영수증 reconciliation 의미를 변경해 우회하지 않는다.

| 단계 | 우선순위 | 후속 구현 작업 | 완료 기준 |
| --- | --- | --- | --- |
| 0 | P0 / 설계 선행 | §6 수정/PII 정책, 기존 null·pending 호환, 변동 발송 계약 확정 | 보안 우회·미정 API 계약 없이 구현 가능 |

요구의 충돌을 숨기거나 현재 보안 조건을 조용히 완화하지 않기 위한 설계 결정 목록이다. 아래 제안은 아직 구현한 기능이 아니다.

| 항목 | 충돌/근거 | 권장 결정 방향 |
| --- | --- | --- |
| 주소 제거와 추출 후 수정 | “주소 수동입력 완전 제거”와 “추출 결과 수정 가능”이 함께 요청됨 | 분석 전 주소 필드/매칭은 완전 제거. 분석 후 자동입력 결과의 정정은 별도 확인 UI로 해석하되, 허용 범위와 저장 계약을 설계에 명시 |
| 소유자·고유번호 수정 | 사용자가 ownerName을 자신의 이름으로 바꾸면 소유자 대조를 우회. 고유번호 변경은 다른 물건 감시로 전환 가능 | PDF 추출 기준 `ownerName/commUniqueNo`는 서버 원본으로 유지. 수정 UI는 제공하되 핵심 식별 정정은 교체 PDF 재분석으로 확정하는 안 우선. 임의 수정값을 기준값으로 저장하는 안은 채택하지 않음 |
| 마스킹과 원문 편집 | 현재 인증 전 원문 고유번호·소유자를 반환하지 않음. 전체 원문 자동입력/편집은 기존 공개 경계를 바꿈 | 인증 전 마스킹 유지·정정 요청 가능, 원문 확인은 인증된 동일 초안에 제한하는 안 검토. 인증 후 정정을 확정하려면 기존 초안을 변경하지 않고 새 초안 생성·재분석·재인증으로 진행. 원문 편집 시점과 결제 전 재확인 UI를 정해야 하며 단순 평문 DTO 확장으로 해결하지 않음 |
| 기존 레코드 호환 | 분석 직후 role 미선택과 과거 null 레코드가 같은 저장 표현을 사용 | 배포 경계/기존 주문 존재/생성 시점 등 명확한 구분 정책을 설계. 새 초안이 기존 건 예외로 통과하지 않도록 검증 |
| 역할 저장 시점 | 분석 후 선택하므로 createDraft 시 owner 검증 불가 | identity/start apply에서 역할 확정, OTP 성공 후 주문 전 비교. 인증/주문 시작 뒤 변경 금지 |
| 변동 알림 발송 | 현재 outbox는 만료 안내 전용이고 사건 단위 유일키 없음 | 우선 역할별 메시지 생성·화면 반영 계약 확정. 문자까지 제공할 경우 사건 식별/영속/중복방지 설계를 먼저 확정하며 추가 DB 필요 시 별도 범위로 제시 |

특히 **모든 추출값을 자유롭게 수정·저장 가능**과 **PDF 원본 기반 소유자 검증·기존 마스킹 유지**를 동시에 만족한다고 선언하지 않는다. 사용자 요구의 “수정 가능”을 누락하지 않고, 실제 수정 확정 방식까지 후속 설계의 P0 산출물로 둔다.

### 7.2 후속 구현 검증 명령

```sh
npx vitest run --config lib/guest-monitoring/vitest.config.ts
npm run test
npm run lint
npm run build
```

위 명령은 **후속 구현 단계의 계획**이다. 이 문서 작업에서 실행한 기능 검증으로 보고하지 않는다. DB 통합 테스트는 기존 보호 조건에 맞는 전용 loopback 격리 DB만 사용하고 운영 DB·실제 문자·실제 결제를 테스트 대상으로 사용하지 않는다. 현재 Vitest는 node 환경이므로 UI 자동검증은 적합한 브라우저 검증 환경을 마련하거나 테스트 환경의 명시적 수동 시나리오로 보완한다.

### 7.3 Codex 교차검수

- 기획 단계: 독립 Codex 검토자가 원본 코드와 본 문서를 대조해 주소 제거 누락, 수정값 신뢰, 역할 저장 시점, OTP 보증 범위, 알림 실구현 범위, DB 수동 적용 제약을 검토한다. 결과는 본 문서에 반영한다.
- 이번 기획 교차검수 결과: 독립 Codex가 원본 코드와 문서 전체를 대조했고 중대 누락 없음으로 검토했다. 인증 전 편집 capability, 주문 조기 반환 전 검증, 결제 후 방어 검증 실패의 `needs_review` 처리, 인증 후 정정 시 새 초안·재인증 경계를 보강했다. §6의 미정 설계 항목은 기획 검수 완료와 별개로 남아 있다.
- 구현 단계: 작성자와 독립된 Codex가 diff와 테스트 결과를 확인한다. 직접 API 호출로 owner 비교/역할 검증을 우회할 수 있는지, 기존 주문 복구가 끊기는지, PII가 확대 노출되는지를 우선 검수한다.
- 완료 조건: §6의 P0 결정이 설계에 반영되고 §7 테스트 증거가 있으며, 중대한 미해결 검수 항목이 없어야 기능 완료로 보고한다. 구현·운영 ALTER·배포 완료를 기획 문서 완료와 혼동하지 않는다.
