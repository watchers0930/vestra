# 회원 구독 연동 기획서

> 작성일: 2026-10-16
> 상태: 기획 초안 / 코드·DB·배포 변경 없음
> 대상: 회원 선불 기간제 구독. 파일명 `guest.plan.md`는 요청된 산출물 경로이며 비회원 기능 개편을 의미하지 않는다.

## 1. 기능 개요

회원이 역할에 맞는 플랜과 이용 기간을 선택하고, PortOne V1 다날 단건 결제를 서버에서 검증한 뒤 구독을 활성화하거나 연장한다. 자동청구 없이 선불 수동 재결제로 운영한다. 결제 주문은 신규 `SubscriptionOrder`로 관리하며, 기존 비회원의 주문생성 → 결제콜백 → 서버검증 → 활성화 패턴만 참고한다.

개인은 무료 가입을 완료한 뒤 원할 때 `/pricing`에서 PRO를 구매한다. 신규 사업자는 가입 → 사업자정보/인증 → 플랜선택 → 결제의 연결된 4단계 위저드를 이용한다. 도입 전 기존 회원 전원은 grandfather 대상으로 현상 유지하며, 강제 구독·일괄 잠금을 적용하지 않는다.

### 1.1 절대 보호 범위

- `GUEST_SINGLE_MONITORING`은 현재 1건·1개월·10,000원(KRW), 가격 버전 `2026-10-15` 그대로 유지한다. 이 상수의 값을 바꾸거나 회원 가격 산정에 사용하지 않는다.
- `GuestMonitoringOrder`, `lib/guest-monitoring/*`, `lib/danal/portone-v1.ts`의 `portoneV1Provider`, 비회원 API·SDK 실행·다날 단건 흐름은 읽기만 한다. 수정·삭제·되돌림·공용화 리팩터링을 금지한다.
- 회원 가격·주문·검증·활성화는 `lib/member-subscription/*` 등 신규 회원 전용 경로에 작성한다. 비회원 주문 서비스·공급자 selector·서명 헬퍼를 호출해 회원 주문을 처리하지 않는다.
- 재사용 허용 범위는 `lib/danal/iamport-rest.ts`, `portone-v1-config.ts` 등 저수준 결제 plumbing과 CSP 설정이다. 이를 재사용한다는 이유로 비회원 동작이나 테스트 게이트를 변경하지 않는다.
- 이 단계의 변경 파일은 본 문서 하나다. Prisma 스키마·SQL·환경변수·실제 결제·운영 DB·기능 코드를 변경하지 않는다.

### 1.2 범위와 제외

| 포함 | 제외 |
| --- | --- |
| 회원 가격 SSOT, 주문·검증·영수증, 선불 구독, 체험, 역할 게이트, 만료·grace·잠금, 가격표·마이페이지 | 비회원 결제 변경, 자동결제·빌링키·자동청구, 다른 PG 도입 |
| 신규 가입·신규 사업자 전환 위저드, 기존 회원 호환 정책 | 기존 회원 강제 이관·일괄 재인증·일괄 잠금 |
| DB 변경 설계와 적용 전 확인 절차, 실결제 선행조건 | 운영 DDL 실행·마이그레이션 실행·채널 실결제 전환 |

## 3. 상품·가격 정책

### 3.1 역할과 플랜

| 회원 유형 | 코드 | 선택 가능 플랜 | 월 기준가 | 등기감시 한도 |
| --- | --- | --- | --- | --- |
| 개인 | PERSONAL | FREE / PRO | FREE 0원 / PRO 9,900원 | FREE 0건 / PRO 5건 |
| 임대사업자 | 현재 코드 RENTAL_BIZ | PRO / PREMIUM 필수 | PRO 9,900원 / PREMIUM 29,900원 | 5건 / 20건 |
| 기업 | BUSINESS | PRO / PREMIUM 필수 | 동일 | 동일 |
| 부동산 중개사 | REALESTATE | PRO / PREMIUM 필수 | 동일 | 동일 |

요구사항의 사업자 범주에는 실제 코드의 `RENTAL_BIZ`도 포함한다. 역할 코드를 일괄 BUSINESS로 바꾸지 않는다. `BUSINESS` 역할과 과거 `BUSINESS` 구독 플랜은 다른 개념이다. ADMIN/LAWYER 등 비대상 역할의 기존 권한은 유지하며, 개인 PREMIUM·사업자 FREE 구매는 서버에서도 거부한다. 신규 플랜 외 AI 분석·상담·SLA 등의 혜택을 임의로 추가하지 않는다.

### 3.2 플랜×기간 실제 선불 가격

회원 전용 `lib/member-subscription/pricing.ts`에 플랜, 기준가, 기간, 할인율, 역할 조건, 감시 한도, `priceVersion`을 정의한다. 서버가 `월 기준가 × 개월 수 × (100 - 할인율) / 100`으로 KRW 정수 총액을 결정한다. 아래 조합은 모두 정수로 산출되며 소수 발생 시 임의 반올림 대신 설정 오류로 차단한다. VAT 포함 표기를 유지하는 안이며, 출시 전 사업 담당자가 최종 표시 기준을 확인한다.

| 기간 | 개월 수 | 할인율 | PRO 선불 총액 | PREMIUM 선불 총액 | 구매 조건 |
| --- | ---: | ---: | ---: | ---: | --- |
| 1개월 유료 체험 | 1 | 0% | 9,900원 | 구매 불가 | 개인 PRO 전용, 일반 갱신 상품과 구분 |
| 3개월 | 3 | 0% | 29,700원 | 89,700원 | 해당 역할의 선택 가능 플랜 |
| 6개월 | 6 | 10% | 53,460원 | 161,460원 | 동일 |
| 9개월 | 9 | 15% | 75,735원 | 228,735원 | 동일 |
| 1년 | 12 | 20% | 95,040원 | 287,040원 | 동일 |
| 2년 | 24 | 30% | 166,320원 | 502,320원 | 동일 |

FREE는 기간 구매·결제 주문 없이 이용한다. UI는 월 기준가·기간·할인·선불 총액을 함께 표시하고, 월 기준가가 매월 자동 청구되는 것으로 표현하지 않는다. 클라이언트는 plan/기간 코드만 요청하며 amount·할인율·감시 한도·역할·시작/종료일을 결정하지 못한다. 주문에는 생성 당시 가격 버전과 금액을 저장하고 이후 가격 변경에도 해당 유효 주문의 스냅샷으로 검증한다.

### 3.3 7일 무료체험과 1개월 유료 체험

7일 무료체험 제공은 필수다. 대상·횟수·시작 시점은 명시되지 않았으므로 다음을 **후속 설계 제안**으로 둔다. 무료체험은 결제 승인 없는 유료 active와 구분된 `trialing` 권한이며, Payment 영수증이나 paid 주문을 만들지 않는다.

- 최초 체험 적격 회원에게 계정당 1회 7일 제공한다. 개인은 `/pricing`에서 명시적 신청, 사업자는 인증 완료 후 플랜선택을 거쳐 4단계의 체험 선택으로 시작한다. 개인 가입 시 자동 PRO 체험이나 결제를 강제하지 않는다.
- 선택한 허용 플랜의 한도(PRO 5건 / 사업자 PREMIUM 20건)를 체험 기간에 제공한다. 서버의 체험 사용 이력을 원자적으로 기록해 재가입 이외의 역할 변경·플랜 변경·중복 요청으로 체험을 재발급하지 않는다. 재가입 악용 식별 기준은 별도 확정한다.
- 사업자 4단계는 기본적으로 선불 결제 단계다. 최초 7일 체험을 선택한 경우에만 결제를 유예하고 `trialing`으로 위저드 완료를 허용한다. 카드·빌링키는 수집하지 않으며 종료 시 자동 결제하지 않는다.
- 체험 중 결제 시 남은 체험을 유료 기간 뒤에 더하지 않고 결제 적용 시점부터 유료 기간을 시작하는 안으로 제안한다. 결제 전 전환일·종료일을 안내한다.
- 개인 1개월 PRO는 9,900원의 **유료 체험 상품**으로 7일 무료체험과 별개다. 계정당 1회 구매를 제안하며, 취소/실패 주문은 사용으로 계산하지 않는다. 기존 회원의 이용 가능 여부는 무료체험 적격 기준과 함께 확정한다.

| US-08 | 결제 후 창이 닫혀도 구독을 확인하고 싶다 | 같은 주문 조회·재검증으로 복구, 중복 결제·중복 기간 적용 없음 |
| US-09 | 만료일과 영수증을 확인하고 재구독하고 싶다 | 마이페이지에서 현황·기한·이력·재구독, 사업자 잠금 중에도 접근 가능 |

### 4.1 개인 가입

`가입/OAuth → 개인 유형(TENANT/LANDLORD) 선택 → 가입 완료(FREE)`로 끝낸다. 완료 화면에서 PRO를 선택 사항으로 안내하되 가입 절차에 결제 단계를 끼워 넣지 않는다. `/pricing`은 `/renewal/pricing`의 동일 회원 상품 화면으로 연결하거나 공통 회원 컴포넌트를 사용해 가격·조건이 달라지지 않게 한다.

### 4.2 사업자 4단계 위저드

| 단계 | 화면과 서버 상태 | 다음 단계 조건 |
| --- | --- | --- |
| 1. 가입 | 계정 생성·신청 유형 저장, 진행바 1/4 | 로그인 및 회원 생성 완료 |
| 2. 사업자정보/인증 | 사업자번호·상호·대표자, 기존 관리자 인증 절차, 진행바 2/4 | 서버 verifyStatus=verified. 대기는 여기서 이어하기 |
| 3. 플랜선택 | PRO/PREMIUM·3/6/9/12/24개월, 총액·체험 조건, 진행바 3/4 | 인증·역할·기간 적격성 검증 및 선택 저장 |
| 4. 결제 | 최종 주문 요약·결제/서버 검증·완료, 진행바 4/4 | appliedAt 확인 후 유료 active, 또는 적격 7일 trialing |

각 단계는 분리된 화면/라우트로 제공한다. 한 페이지에 가입·인증·선택·결제 폼을 함께 나열하지 않는다. 새로고침/OAuth 복귀/재로그인에도 서버의 신청 상태로 재개한다. URL·sessionStorage의 intendedRole/step은 화면 복구 힌트일 뿐 권한 근거로 삼지 않는다. 뒤로가기나 플랜 변경 시 미완료 주문을 먼저 확인하며 새 결제를 자동 실행하지 않는다.

기존 계정의 사업자 전환은 1단계를 계정 확인 완료로 표시하고 2단계부터 시작한다. 기존 인증 승인 동작을 결제 승인으로 간주하지 않으며, 인증 역할과 사업자 유료 기능 접근은 별도 서버 가드로 결합한다.

### 4.3 가격 페이지와 마이페이지

- `/renewal/pricing`: FREE/PRO/PREMIUM 설명, 감시 0/5/20건, 전체 기간별 총액, 할인율, 적격 체험, 결제 버튼, 수동 갱신·자동청구 없음 안내. 비로그인은 로그인 후 선택을 복원한다.
- 개인에게 PREMIUM, 사업자에게 FREE/1개월 유료 체험은 구매 불가 사유와 함께 표시하거나 선택에서 제외한다. 서버에서도 같은 제한을 적용한다.
- `/profile?tab=tier`: 역할/사업자 인증과 구독을 구분하고 현재 플랜·trial/active/grace/locked·시작일·만료일·감시 사용량/한도·영수증·재구독 CTA를 표시한다.
- 재구독 CTA는 마지막 적격 플랜·기간을 미리 선택해 결제 확인으로 연결한다. 가격 변경 시 현재 총액을 다시 확인받고 사용자의 명시적 결제로 진행한다. 클릭 즉시 과금하는 방식은 아니다.
- `grandfather` 회원은 기존 이용 상태와 선택적 구독을 안내한다. 시스템이 구독 미보유를 결제 오류나 잠금으로 표시하지 않는다.

## 5. 기존 회원 보호·역할 게이트

### 5.1 정책 적용 시점

도입 시점을 `policyEffectiveAt`, 적용 버전을 `policyVersion`으로 고정한다. 도입 전에 생성된 회원 전원에게 서버에서 grandfather 이력을 기록한다. 기존 FREE/유료/사업자/인증대기/구독 미보유 회원을 일괄 새 가격·플랜으로 이관하지 않는다. 정확한 도입 시각은 출시 때 확정하며 현재 문서에서 임의 날짜를 부여하지 않는다.

| 대상 | 적용 정책 |
| --- | --- |
| 기존 회원, 도입 후 신규 사업자 신청 없음 | 기존 상태 유지. 새 강제구독·grace·잠금 규칙 제외 |
| 기존 회원의 도입 전 사업자 신청/승인 대기 | 기존 신청 기준 유지. 승인 시점만으로 새 게이트 적용 금지 |
| 도입 후 신규 개인 가입 | FREE/PRO, 가입 시 결제 강제 없음 |
| 도입 후 신규 사업자 가입 | 인증 및 PRO/PREMIUM 구독 필수. 최초 무료체험 예외는 §3.3 제안 |
| 기존 회원의 도입 후 신규 사업자 역할전환 신청 | 해당 신청부터 새 사업자 게이트 적용. 과거 계정 생성일로 우회 불가 |
| 기존 회원의 자발적 구독 | 구입한 기간/플랜의 추가 권한만 적용. 구독 만료 후 기존 기준선 복원, 강제잠금 금지 |

기존 회원의 자발적 구매는 grandfather 포기로 해석하지 않는다. 반면 신규 사업자 전환 완료로 얻은 새 사업자 권한에는 새 정책을 적용한다. 신규 신청 취소·거절 시 기존 기준선으로 복귀하며, 취소/재신청·개인↔사업자 반복 전환으로 무료체험·grace를 초기화하지 않는다.

### 5.2 권한 판정

`role/인증 상태`, `유료/체험 이용 상태`, `grandfather 기준선`, `신규 역할 신청 정책`을 독립적으로 조회해 유효 권한을 계산한다. PRO 결제로 PERSONAL을 BUSINESS로 승격하거나 PREMIUM 결제로 중개사 인증을 대신하지 않는다. 역할 승인은 기존 인증 경로에서만 수행한다.

UI 이동 제한만으로 게이트를 구현하지 않는다. 회원 신규·변경 API, 사업자 기능 API, 감시 등록 및 회원 감시 배치에서 같은 유효 권한 정책을 사용한다. JWT의 과거 plan/role이나 dailyLimit을 단독 승인 근거로 쓰지 않는다. 기존 `ROLE_LIMITS`를 전역 변경하거나 비회원 배치 공통 경로를 개편하지 않는다.

기존 `BUSINESS` 구독 문자열과 기존 감시 한도는 호환 분기로 보존한다. 새 주문에서만 `PREMIUM`을 사용하며 과거 플랜의 일괄 rename·과거 가격 재계산은 하지 않는다. 레거시 구독이 저장소 판별 방식으로 보유하던 권한도 새 만료 가드를 일괄 적용해 축소하지 않는다.

`iamport-rest.ts`의 내부적인 비회원 오류 클래스 의존성은 현상 그대로 둔다. 회원 코드가 비회원 도메인 서비스를 import하는 것은 금지하되, 허용된 저수준 모듈 내부의 기존 전이 의존성을 제거하려고 보호 파일을 수정하지 않는다. 회원 경계에서 외부 오류를 회원용 오류 코드로 변환한다.

### 6.2 결제·검증·활성화

1. 로그인 회원의 DB 역할/인증·정책·체험/구매 이력·기간 적격성을 확인한다. 사용자별 잠금과 멱등키로 생성 요청을 직렬화하고 미완료 주문을 재사용한다. 같은 멱등키의 다른 사용자·상품 요청은 거부한다.
2. 서버 SSOT로 금액을 결정해 `SubscriptionOrder`에 스냅샷을 저장한다. 회원 전용 `msub_` 주문번호를 사용하고 V1 `merchant_uid`로 전달한다. 주문 TTL은 비회원 값을 참조하지 않고 회원 설정으로 정의한다.
3. 회원 전용 purpose(예: `member_subscription_payment_v1`)와 키 도메인으로 userId·orderId·플랜·기간·금액·통화·가격 버전·채널 환경·만료·nonce를 서명한다. 비회원 purpose/서명을 받아들이지 않는다. SDK 비밀키는 브라우저에 전달하지 않는다.
4. 브라우저의 success/amount/merchant_uid는 승인 근거로 쓰지 않는다. 세션·소유권·서명·nonce를 검증한 뒤 `imp_uid`로 V1 서버 재조회한다.
5. 조회 결과의 거래 ID·주문번호·정수 금액·KRW·PG·MID·결제수단·테스트/운영 환경·paid 상태·승인 시각·취소 금액/이력을 대조한다. 승인 시각은 주문 생성 이후·TTL 이내·현재 이하이어야 한다. 미승인에 paidAt을 만들지 않는다.
6. 비회원 검증 패턴처럼 승인 기록 직전에 독립적인 두 번째 REST 조회를 수행한다. 두 조회의 주문/거래/최종 상태 불일치·부분취소·모호한 응답은 활성화하지 않는다. 실패·취소도 최종 상태 재확인 후 기록한다.
7. 거래 ID unique와 현재 상태 조건부 갱신으로 nonce 소비·승인 증빙·paidAt을 먼저 영속화한다. 그 다음 사용자/주문 잠금 아래 Subscription 생성/연장 + Payment(completed) 생성 + 적용 기간/appliedAt 기록을 하나의 DB 트랜잭션으로 처리한다.
8. `paid && appliedAt=null`은 회원 전용 복구 작업이 재적용한다. 영수증 중복·구독 기간 중복 증가를 unique/잠금/appliedAt으로 막는다. 이미 적용된 동일 거래의 콜백은 멱등 응답하고, 다른 거래의 재사용·needs_review 재승인은 차단한다.

회원·비회원 간 동일 imp_uid 재사용도 차단해야 한다. 각 테이블의 unique만으로 교차 중복이 방지된다고 보지 않는다. 회원 검증 시 기존 비회원 거래 점유 여부는 읽기 조회만 하고, 회원 전용 주문 prefix·서명·`merchant_uid`의 정확한 일치 검증으로 교차 적용을 거부한다. 비회원 결제 테이블에 회원 거래를 삽입하지 않는다.

### 6.3 상태·장애·복구

- 주문 상태: `pending → paid → appliedAt 설정`. 실패/취소는 `failed/canceled`, 영구 적용 충돌은 `needs_review`, 확인된 환불은 `refunded`. 주문의 paid와 구독 active는 다른 상태다.
- SDK 호출 전 로드/init 실패는 같은 주문 재시도를 제공한다. request_pay 이후 응답 유실·닫기·네트워크 오류는 승인 불명확으로 서버 조회부터 수행하며 새 주문/결제창을 자동 생성하지 않는다.
- 모바일 복귀의 imp_uid·merchant_uid는 미신뢰 입력이다. 세션 복구 후 본인 주문과 대조·서버 재검증하며 식별자 쿼리는 처리 후 제거한다. 서명·nonce·PII를 URL/웹 저장소에 보관하지 않는다.
- imp_uid 유실은 인증된 복구 API에서 merchant_uid로 후보를 탐색한 뒤 단건 조회와 전체 검증을 다시 수행한다. 후보가 여러 개이면 needs_review로 두며 임의 선택하지 않는다.
- 세션 401은 재로그인 후 기존 주문 재개, pending 409/429/503/네트워크 오류는 재조회, 400/403/404 등의 영구 거부는 안내를 보존한다. GET pending이 영구 거부를 단순 승인 대기로 덮어쓰지 않는다.
- 적용 충돌·paid 미적용·취소/환불 상태 불일치를 내부 확인 큐로 노출한다. 승인 확인 없이 자동 환불하거나 성공으로 표시하지 않는다. 일반 환불 UI는 별도 범위이지만 취소/환불 감지·권한 정합성 확인은 출시 필수다.

### 6.4 보안

- 로그인 기반 모든 주문/조회/복구에서 서버 userId로 소유권을 제한한다. 클라이언트 userId·requestedRole·신청 step을 신뢰하지 않는다.
- 상태 변경에 CSRF 보호를 적용한다. `lib/csrf.ts`는 Origin/Referer 검증 기반이므로 회원 결제에는 명시적 허용 Origin을 요구하고, 잘못된 Origin을 Referer로 우회 허용하지 않는 추가 검증을 신규 경로에 둔다. 세션 쿠키·SameSite·strict 스키마·요청 제한을 함께 사용한다.
- 결제용 HMAC과 nonce의 유효기간/1회 소비를 검사한다. 만료/소비 문맥의 재전송은 이미 기록된 동일 거래의 멱등 복구만 허용한다. 공급자 웹훅은 브라우저 콜백 CSRF 예외로 혼용하지 않는다. 웹훅을 추가할 경우 별도 공급자 인증 및 동일 서버 재조회가 선행되어야 한다.
- 서버 조회는 허용 REST 호스트·timeout·no-store를 유지한다. 영수증 URL은 검증된 공급자 값만 사용하며 허용 스킴/호스트를 확인하고 임의 URL을 서버에서 fetch하지 않는다.
- 로그/분석 도구/URL에 개인정보·REST 원문·imp_uid·토큰·서명·nonce·시크릿을 남기지 않는다. 내부 주문 식별자·정제 상태·실패 사유만 감사 기록한다.
- 테스트/mock 거래는 운영 회원의 유료 권한을 만들 수 없다. 테스트는 격리 DB·계정으로 검증하며 운영에서는 확인되지 않은 채널/환경을 503으로 차단한다.

## 7. 기간·만료·갱신 정책

### 7.1 시작·종료·연장

최초 결제 적용은 `startDate=서버 now`, `endDate=now+선택 개월`, `status=active`다. 같은 플랜을 만료 전에 재결제하면 기존 startDate를 보존하고 `max(now, 기존 endDate)`부터 구매 기간을 추가한다. 만료 후 재구독은 now부터 시작하고 지난 미이용 공백을 소급 과금하지 않는다. 적용한 구간은 주문에 별도로 남긴다.

기간은 30일 고정 곱셈이 아닌 달력 개월로 계산하며, 월말은 대상 월의 마지막 유효일로 보정하는 안을 제안한다. 저장/비교는 UTC, 표시는 Asia/Seoul로 통일하고 `now < endDate`를 유효 경계로 사용한다. 7일은 168시간으로 구분한다. 달력 기준과 체험 전환 방식은 후속 상세 설계에서 고정하고 월말·윤년 테스트를 둔다.

활성 기간 중 다른 플랜으로 변경할 때 잔여기간 정산이 필요하므로 MVP는 동일 플랜 연장만 허용하는 안을 제안한다. 만료 후에는 역할상 허용된 다른 플랜을 구매할 수 있다. 즉시 업그레이드/다운그레이드·차액 환불·중첩 구독은 별도 설계 전 제공하지 않는다.

### 7.2 상태 전이

| 대상 | 만료 처리 | 권한·데이터 처리 |
| --- | --- | --- |
| 신규 개인 유료/무료체험 | endDate/trialEndsAt 도달 시 FREE | 데이터 보존. 유료 감시 실행/신규 등록은 중지, 기존 결과 조회 가능 |
| 새 정책 사업자 유료/무료체험 | 만료일부터 7일 grace, 이후 locked | grace 동안 기존 이용을 유지하는 안. grace 종료 후 사업자 기능·회원 감시 실행 중지 |
| grandfather 기존 회원 | 새 강제 만료/잠금 규칙 제외 | 자발적 구독 종료 시 보호된 기존 기준선 복원 |
| grandfather의 신규 사업자 전환 권한 | 해당 신청의 새 정책 적용 | 새 사업자 권한에 grace/잠금 적용, 기존 개인 기준선 이용은 보존 |

grace는 `기존 endDate 또는 trialEndsAt + 7일`로 고정하고 로그인/배치 지연/재접속으로 연장하지 않는다. cron이 늦어도 요청 시 현재 시각으로 잠금을 판정한다. 체험 종료에도 사업자 grace를 적용하는 것은 제안이며 최종 확정이 필요하다.

잠금은 계정 전체 로그인 금지가 아니라 해당 사업자 유료 기능의 이용 제한이다. 로그인·마이페이지·본인 데이터 읽기/내보내기·결제/재구독·고객지원·계정 관련 기본 기능은 유지한다. 재결제 적용 즉시 새 만료일 기준으로 잠금을 해제한다. UI와 서버 API·회원 감시 배치가 같은 정책을 적용해야 한다.

등기감시 대상·분석·자산·이력은 삭제하지 않는다. 20건 보유 후 PRO 5건으로 재구독하는 등 한도 초과 시 사용자가 활성 대상 5건을 선택하고 나머지는 보관/중지하며 새 등록을 막는다. 기존 grandfather가 가진 감시 권한은 새 구독 만료로 축소하지 않는다. 감시 중지 공백에 대해 소급 감시 완료를 표시하지 않는다.

### 7.3 수동 재결제와 해지

자동 결제수단 저장·스케줄 청구가 없다. 만료 전/당일/grace/잠금 화면에서 재구독을 안내하고 사용자 승인으로 매번 단건 결제한다. 알림은 회원 전용 만료 기준 멱등키로 중복을 막고 기존 비회원 만료 메시지·작업 큐를 사용하지 않는다.

선불 구독의 해지/종료 요청은 이미 결제한 기간을 즉시 소멸시키거나 역할을 PERSONAL로 바꾸지 않는 안을 제안한다. 일반 해지와 환불 요청을 구분하고, 환불 시 권한 정산·영수증 상태·실제 PG 취소 확인 절차는 출시 전 별도로 확정한다. 기존 cancel API의 즉시 역할 강등 동작을 신규 구독에 그대로 연결하지 않는다.

## 8. DB 스키마 설계 산출물

아래는 후속 상세 설계용 필드 계약이며 실행 가능한 Prisma/SQL 변경이 아니다. 실제 데이터 타입·enum 도입·인덱스 이름·백필 방식은 baseline 대조 후 확정한다. 보호 대상 `GuestMonitoringOrder` 등 비회원 테이블은 변경 대상에서 제외한다.

### 8.1 신규 SubscriptionOrder

| 필드 | 타입/제약(안) | 목적 |
| --- | --- | --- |
| id / orderId | cuid PK / String unique | 내부 키 / 회원 전용 merchant_uid |
| userId | User FK + index | 소유권, 사용자별 직렬화 |
| subscriptionId | nullable Subscription FK | 최초 결제 시 구독 미존재 허용, 적용 시 연결 |
| purpose | initial / renewal | 최초 구독·연장 구분 |
| plan / durationMonths | PRO 또는 PREMIUM / Int | 구매 상품 스냅샷 |
| monthlyPrice / discountPercent / amount | Int / Int / Int | 기준가·할인·총액, KRW 양의 정수 |
| currency / priceVersion / policyVersion | KRW / String / String | 금액·회원 정책 버전 |
| roleAtOrder / roleApplicationId | String / nullable FK | 역할 적격성과 신규 전환 신청 결합 |
| status | pending / paid / needs_review / failed / canceled / refunded | 결제·운영 처리 상태 |
| providerMode / channelEnvironment / merchantConfigVersion | portone_v1 / test 또는 live / String | 환경 혼용·주문 중 채널 변경 차단 |
| providerTransactionId | nullable String unique | 검증한 imp_uid, 거래 재사용 방지 |
| idempotencyKey | String, unique(userId, idempotencyKey) | 같은 요청의 상품 불일치 검증 포함 |
| callbackNonceHash / nonceConsumedAt | String / nullable DateTime | 원문 nonce 장기 노출 최소화, 원자적 소비 |
| verificationEvidence | nullable Json/Text | 정제한 서버 검증 결과·시각, PII 원문 제외 |
| paidAt / expiresAt | nullable DateTime / DateTime | 승인 시각 / 대기 TTL |
| appliedPeriodStart / appliedPeriodEnd / appliedAt | nullable DateTime | 적용 구간·중복 적용 방지 |
| createdAt / updatedAt | DateTime | 감사·복구 |

필수 인덱스: `(userId, status)`, `(status, expiresAt)`, `(status, appliedAt)`. 사용자별 미완료 주문 1개 정책은 트랜잭션/잠금으로 보장하며 필요 시 PostgreSQL 부분 unique 인덱스를 별도 DDL로 검토한다. 영수증/거래 이력의 연쇄 삭제는 금지하는 안으로 두고 계정 삭제·보관 정책을 별도 검토한다.

### 8.2 기존 모델 확장 및 정책 기록

| 대상 | 설계 변경(안) | 호환 원칙 |
| --- | --- | --- |
| Subscription | 신규 plan PREMIUM, trialing 상태, trialStartedAt/trialEndsAt, graceEndsAt/lockedAt, policyVersion, orders 관계 | price는 월 기준가 의미 유지, 선불 총액은 Order/Payment에 저장. 레거시 BUSINESS·null endDate 보존 |
| Payment | nullable subscriptionOrderId unique FK, orders의 정제 receiptUrl 기록 경로, 필요 시 검증 환경 구분 | 기존 orderId unique 유지, 과거 결제 재작성 금지. paid 주문 적용 시 정확히 1개 completed 영수증 |
| User 관계 | subscriptionOrders, membershipPolicy, roleApplications 관계 추가 | role은 결제 상품에 의해 자동 변경하지 않음 |
| 신규 MemberSubscriptionPolicy | userId unique, policyVersion, grandfatheredAt, legacyEntitlementsSnapshot, trialUsedAt | 기존 권한 기준선·체험 1회 소비 기록. 스냅샷은 필요한 최소 값만 저장 |
| 신규 MemberRoleApplication | id, userId, requestedRole, requestedAt, policyVersion, status, verifiedAt, completedAt | 도입 전 대기 신청과 도입 후 새 신청 구별. 기존 requestedRole/verifyStatus와 연결 |

trial 사용 여부는 Subscription 삭제/변경으로 초기화되지 않는 정책 레코드에 보존한다. FREE 개인은 Subscription이 없어도 FREE로 조회할 수 있으며 무료 영수증을 만들지 않는다. grandfather 기준선은 역할·플랜·한도 등 실제 필요한 권한을 명시적으로 보존하되 민감 원문을 복제하지 않는다.

DB 불변식: paid는 검증 거래 ID·paidAt·서버 증빙 필수, appliedAt이 있으면 적용 기간·구독 연결·완료 Payment가 존재해야 한다. endDate는 startDate보다 뒤이며, 주문 금액/기간/환경은 생성 후 클라이언트 요청으로 바뀌지 않는다. DB 제약으로 가능한 부분과 트랜잭션으로 보장할 부분을 상세 설계에서 나눈다.

### 8.3 운영 적용 전 절차

1. **대장 확인 전 운영 변경 금지.** 현재 운영 DB는 Prisma Migrate 미관리이며 `prisma/migrations`/baseline이 없는 전제를 실제 상태와 대조한다. 운영 구조 변경 명령을 자동 실행하지 않는다.
2. 운영 스키마·제약·인덱스·기존 구독/대기 역할 데이터의 읽기 전용 현황과 코드 스키마 차이를 확인한다. baseline SQL/현재 상태 기록을 만들고, Migrate 관리로 전환할지 승인된 수동 SQL로 추가할지 별도 결정한다. 과거 테이블 생성 SQL을 운영에 재실행하지 않는다.
3. 운영과 분리된 preview DB에서 baseline 재현 → 추가 DDL diff 검토 → nullable/기본값·unique 충돌·쿼리 계획·구버전 호환성을 검증한다. 비회원 테이블 DDL/데이터 변경이 없는지 확인한다.
4. 기존 회원 분류·기존 권한 기준선·도입 전 대기 신청의 백필을 dry-run으로 검토한다. 도입 경계의 동시 가입/신청이 누락되지 않도록 배포 플래그·기준 시각·서버 정책 레코드 생성 순서를 설계한다. 미분류 기존 회원을 신규 잠금 대상으로 취급하지 않는다.
5. 백업/스냅샷, 적용·검증·중단 계획을 준비하고 대장 확인을 받은 후 운영 DDL/백필을 별도 실행한다. 실제 결제 기록을 삭제하는 롤백은 사용하지 않는다. 장애 시 신규 회원 주문을 중지하고 기록을 보존한다. 비회원 코드의 되돌림도 금지한다.
6. 테스트 배포에서 권한/결제/기존회원 회귀를 검증한 뒤 운영 승격은 별도 지시에 따른다. 본 기획 작업에서는 위 절차를 실행하지 않는다.

## 9. 테스트 채널과 회원 실결제 전환 선행조건

현재 공용 채널은 테스트 채널만 열린 상태다. 저장소에서는 `verifiedV1TestChannels=[]`이므로 키가 있어도 config 게이트가 503을 반환할 수 있다. **테스트 자격증명 보유·테스트 코드 통과·실제 무출금 테스트 성공·회원 운영 실결제 가능은 각각 다른 완료 조건**이다.

회원 테스트는 허용된 기존 config/REST 인터페이스와 격리 fixture/DB로 설계한다. 실제 테스트 연동은 테스트 채널 증빙과 정확한 V1 응답·SDK·CSP 확인 후에만 수행한다. 공용 allowlist/환경변수를 임의로 열거나 sandbox 검증을 없애서 우회하지 않는다.

회원 실결제는 다음을 충족하는 **별도 선행 작업**으로 분리한다.

- 회원 선불 상품에 사용할 운영 계약/채널/MID·수단·운영 자격증명 및 테스트/운영 응답 판정 기준 확인.
- 현재 `getPortoneV1Config()`와 REST 호출이 공용 테스트 게이트에 묶여 있으므로, 보호된 비회원 동작을 유지하면서 회원 live 설정을 전달할 수 있는 plumbing 계약을 별도 설계·검토. 현재 구현 그대로 live 호출이 가능하다고 가정하지 않는다.
- 실결제를 위해 공용 설정을 바꾸어 비회원 테스트 채널·키·상태 판정이 함께 전환되는 방식은 금지. 기존 인터페이스/비회원 채널을 보존할 수 없는 경우 출시를 보류하고 별도 범위 결정을 받는다.
- 운영 회원 권한이 테스트/mock 승인으로 생성되지 않는 환경 차단, 회원 전용 기능 플래그, 가격·취소/환불·약관/동의·영수증 표시 확정, 운영 DB 절차 완료.
- preview에서 PC/모바일 결제·중단·복구·재구독·CSP 확인, 운영 채널 검증 계획과 대장 확인. 현 기획은 실결제 활성화 권한이나 완료 선언을 포함하지 않는다.

## 10. 우선순위와 구현 순서

P0는 보안·기존 회원 보호·출시 차단 조건, P1은 사용자 흐름 완성에 필요한 필수 기능, P2는 별도 후속 확장이다. P1도 이번 기능 출시 전에 완료해야 한다.

| 순서 | 우선순위 | 작업 | 완료 기준 |
| --- | --- | --- | --- |
| 1 | P0 | 보호 범위·기존 데이터·도입 기준·체험/기간 정책 확정 | 비회원 무변경 경계, grandfather/신규 신청 판정표 확정 |
| 2 | P0 | 회원 SSOT·역할/기간 검증·독립 서비스 계약 | 전체 가격표 일치, 개인/사업자 부적격 조합 거부 |
| 3 | P0 | DB 상세 설계·baseline/preview·백필 계획 | 대장 검토 가능한 DDL diff·검증/백업/중단 계획 확보 |
| 4 | P0 | 주문·HMAC·서버 재조회·nonce·멱등 적용·Payment | 서버 검증 없이 active 불가, 승인 1건당 영수증/기간 1회 |
| 5 | P0 | grandfather 가드·기존 API 우회 차단·만료/grace/잠금 | 기존 회원 현상 유지, 새 사업자 게이트·7일 경계 서버 보장 |
| 6 | P1 | 개인 무료 가입·사업자 4단계·가격표·마이페이지 | 진행바·재개·역할 제한·총액·만료일·재구독 사용 가능 |
| 7 | P1 | 7일 체험·수동 갱신·알림·결제 장애 복구 | 1회 적격 체험, 자동청구 없음, 모바일/중복 요청 복구 |
| 8 | P0 출시 조건 | 테스트 증빙·기존 회귀·실결제 별도 선행 작업 | 테스트 완료와 live 가능을 구분, 승인 전 실결제 비활성 |
| 후속 | P2 | 기간 중 플랜 변경 정산·일반 환불 UI·추가 운영 통계 | 별도 요구·정책 확정 후 착수. 자동청구는 본 범위 제외 |

후속 구현에서 회원 전용 단위/통합/브라우저 테스트, 기존 관련 회귀, 타입 검사·lint·빌드를 수행한다. fixture 통과를 실제 PG·운영 검증으로 대체하지 않는다. 본 단계에서는 정적 코드 분석과 문서 검토만 수행한다.

## 12. 후속 상세 설계에서 확정할 사항

| 항목 | 현재 제안 / 필요한 결정 |
| --- | --- |
| 무료체험 대상 | 계정당 최초 1회, 개인 선택·사업자 인증 후 시작. 기존 회원 포함 여부·재가입 식별 기준 확정 |
| 1개월 유료 체험 | 개인 PRO 계정당 1회 제안. 재구매 허용 여부 확정 |
| 사업자 체험 완료·만료 | 결제 단계에서 최초 trial 예외, 체험 종료 후에도 7일 grace 제안 |
| 달력·잔여기간 | 달력 개월/월말 보정·동일 플랜 잔여기간 보존, 체험 중 결제는 now 시작 제안 |
| 플랜 변경·해지·환불 | 활성 기간 동일 플랜 연장만, 선불 기간 보존. 실제 환불과 권한 정산 정책 확정 |
| 사업자 잠금 범위 | 사업자 유료 기능·감시 중지, 본인 데이터 읽기·재구독 유지. API별 적용 목록 확정 |
| grandfather 기준선 | 배포 시 실제 역할/구독/한도 및 도입 전 신청 상태를 읽기 검증, 권한 보존 스냅샷 정의 |
| VAT·영수증 | 현재 VAT 포함 표기를 기준으로 가격/영수증 계약 최종 확인 |
| 운영 DB·실결제 | baseline 방식·운영 적용과 회원 live plumbing/채널 승인 각각 별도 선행 확인 |

필수 요구와 제안을 혼동하지 않는다. 위 미확정 정책은 이번 문서 작성이나 후속 구현 편의를 위해 실제 운영 데이터·보호 코드에 임의 적용하지 않는다.
