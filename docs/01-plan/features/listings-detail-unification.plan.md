## 1. Overview

### 1.1 Purpose

매물검색 목록에서 물건을 클릭했을 때 **물건 종류에 따라 경로가 갈라지는 현재 문제를 제거**하고, 모든 물건이 동일한 **매물 상세보기**로 이동하도록 통일한다.

### 1.2 두 메뉴의 성격 정의 (기준)

| 메뉴 | 성격 | 데이터 원천 |
|------|------|------------|
| **매물검색** | 임대업자·부동산·기업회원이 **올린 매물**이 노출되는 곳 (공급자 등록 매물) | 실제 등록 매물. **단, 현재는 실매물이 없어 테스트용으로 국토부 제공 물건 일부를 임시 노출** |
| **시세지도** | **국토부가 제공하는 시세 DB**를 보여주는 곳 (별개 메뉴) | 국토부 실거래·시세 |

**핵심 원칙**: 매물검색 안에 보이는 물건은 그 출처가 테스트(국토부)든 실제 등록 매물이든 **모두 "매물"로 취급**한다. 따라서 클릭 시 동작도 동일해야 한다. 시세지도는 이 기획의 범위가 아니다.

### 1.3 Background — 현재 문제

매물검색 카드 리스트(`app/(personal-home)/renewal/listings-list/ListingsListClient.tsx`)에서 물건 종류에 따라 클릭 경로가 갈린다.

| 블록 | 현재 클릭 동작 | 코드 |
|------|--------------|------|
| 안심 매물(테스트 샘플) | 매물 상세보기 이동 ✅ | `href=/renewal/listing-db-detail?id=...` |
| 국토부 실거래 9개 | **지도 페이지로 튐 ❌** | `<div onClick={goToMap({aptName, dong})}>` |

같은 매물검색 리스트에 나란히 있는데 하나는 상세보기, 하나는 지도로 튀어 **사용자 혼란**을 유발한다. 국토부 물건은 "시세지도용 데이터"가 아니라 매물검색에 임시로 꽂아둔 매물이므로 상세보기로 가야 맞다.

### 1.4 Related Documents / Files

- 매물검색 리스트: `app/(personal-home)/renewal/listings-list/ListingsListClient.tsx`
- 기존 매물 상세: `app/(personal-home)/renewal/listing-db-detail/`
- 국토부 물건 데이터: `/api/listings/apartments` → `lib/molit-api.ts` (`fetchRealTransactions`, `fetchRecentPrices`)
- 지도(시세지도): `app/(personal-home)/renewal/listings-map/`

## 2. Scope

### 2.1 In Scope

1. 매물검색 카드 클릭 경로를 **매물 상세보기 단일 경로로 통일** (국토부 물건도 상세보기로 이동)
2. 매물 상세보기 페이지 구성 확정
   - CTA: **계약의향**, **AI 권리분석**
   - 정보 섹션: **위치지도**, **인프라**, **학군**, **시세정보**
3. 국토부(테스트) 물건을 상세보기에서 표현하기 위한 식별·데이터 처리 방식 정의

### 2.2 Out of Scope

- **시세지도 메뉴** 자체의 기능/UI (별개 메뉴 — 이번 기획 대상 아님)
- 실제 매물 등록 플로우(임대업자/부동산/기업회원 업로드) — 별도 기획
- 목록 뷰 중 "지도에서 찾아보기" 뷰의 개편 (현행 유지)

## 4. 매물 상세보기 상세 설계

### 4.1 페이지 구성 — **6개 섹션 전체 MVP 포함 (확정)**

| 영역 | 내용 | 데이터 출처 (확정) |
|------|------|------------------|
| 헤더 | 단지/매물명, 주소(법정동), 준공년도, 가격, 매물 배지 | 카드 쿼리 |
| **CTA 버튼** | **계약의향** / **AI 권리분석** | 상단 고정 노출. AI 권리분석은 기존 `/renewal/rights` 연결 (기존 상세에 이미 존재) |
| 위치지도 | 매물 좌표 핀 (카카오) | 국토부 물건은 apartments API가 이미 geocode한 lat/lng 재사용 |
| 인프라 | 주변 편의·교통·생활 인프라 (반경 1km) | **기존 `/api/neighborhood` 재사용** |
| 학군 | 인근 학교·학원·유치원 | **기존 `/api/neighborhood` 재사용** (school SC4 + academy + kindergarten) |
| 시세정보 | 단지 월별 실거래 시세 추이 | `fetchRecentPrices` 재사용 (기존 매물 상세와 동일 로직) |

> ✅ 6개 섹션 모두 기존 API/데이터로 커버 가능 — 신규 데이터 소스 개발 없음.

### 4.2 등록 매물 vs 국토부(테스트) 물건 처리 — **확정**

두 물건 모두 **같은 상세보기 페이지**로 가되, 식별 방식만 다르다.

- **등록 매물**: 고유 `id` 있음 → 기존 `listing-db-detail?id=...` 방식 유지
- **국토부(테스트) 물건**: **안정적 고유 id 없음**(매 요청마다 랜덤 셔플된 임시 id).
  → **결정**: 카드가 가진 정보(`단지명 · 법정동 · 면적 · 층 · 거래일 · 좌표`)를 **쿼리 파라미터로 상세에 전달**하고, 인프라·학군·시세는 상세 페이지에서 **기존 API를 주소 기준으로 호출**한다. **전용 통합 재조회 API는 신설하지 않는다.**

### 4.3 데이터/API — **확정 (신규 API 없음)**

- **시세정보**: 기존 `fetchRecentPrices`(월별 실거래 평균) 재사용
- **위치지도**: apartments API가 이미 카카오 geocode로 lat/lng 확보 → 상세에서 재사용 (없으면 주소로 재 geocode)
- **인프라·학군**: 기존 **`POST /api/neighborhood`** 재사용 (카카오 8개 카테고리 반경 1km + kapt 단지정보 + GPT 코멘트). 입력은 주소 → 국토부 물건은 `법정동 + 단지명`으로 주소 구성해 호출
- **성능**: neighborhood API는 GPT 코멘트까지 포함해 다소 무거우므로 **상세 진입 시 1회 호출 + 결과 캐싱**(`apiCache`)으로 중복 호출 차단. 시세·좌표도 캐싱
- **서버 검증**: 상세 조회에 넘기는 주소/단지명 입력값 서버단 검증, `/api/neighborhood`의 기존 `validateOrigin`(CSRF) 유지

## 5. 플랫폼 개발 5대 원칙 반영

1. **500줄 제한**: 상세보기 페이지는 `헤더`, `CTA`, `위치지도`, `인프라`, `학군`, `시세정보`를 **컴포넌트 분리**하여 페이지 파일 비대화 방지
2. **단일 책임**: UI 컴포넌트 / 데이터 조회 훅 / API 호출 분리
3. **서버 검증·보안**: 상세 조회 API 입력값 서버 검증. 키·토큰 노출 없음
4. **성능**: 시세·좌표 조회 캐싱, 중복 호출·N+1 차단
5. **폴더 구조**: `components`(섹션 UI) / `hooks`(조회·상태) / `app/api`(조회 라우트) 역할 분리
