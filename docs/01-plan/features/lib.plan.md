# 비회원 등기감시 단건 서비스 기획서

> 프로젝트: VESTRA  
> 작성일: 2026-10-15  
> 상태: 기획 초안 · 구현 전  
> 상품: 물건 1건 / 1개월 / 결제 총액 10,000원 / 다날 단건 결제  
> 작업 범위: 기존 코드 분석 및 기획 문서 작성만 수행. 실제 기능 코드, Prisma 스키마, 환경변수, 운영 DB는 변경하지 않는다.

## 1. 기능 개요

회원가입 없이 등기부등본 PDF를 제출하고 10,000원을 결제하면 해당 물건 1건을 1개월 동안 감시한다. 비로그인 사용자가 등기감시를 선택하면 유료 서비스 공지, 기존 회원 요금제, 비회원 신청폼을 같은 화면에서 제공한다. 신청 후에는 이름·전화번호 입력과 다날 휴대폰 본인인증을 거쳐 본인이 신청한 물건의 감시 실행 달력만 확인한다.

감시는 기존 등기신청사건 프리체크 엔진을 재사용한다. 만료 시 Solapi로 연장 결제 안내 문자를 보내고, 결제가 없으면 감시를 자동 종료한다. 자동 정기결제는 제공하지 않는다.

### 1.1 확정 요구사항

| 구분 | 요구사항 |
|---|---|
| 진입 | 비로그인 등기감시 선택 시 유료 공지·요금제·비회원 신청폼을 함께 제공 |
| 신청 | 이름, 전화번호, 주소, 등기부등본 PDF 필수 |
| 자동 추출 | 기존 PDF 파싱 흐름으로 `commUniqueNo`, `ownerName` 추출 |
| 결제 | 다날로 1건·1개월·10,000원 결제 확인 후 감시 등록 |
| 조회 | 이름+전화번호+다날 본인인증 세션을 모두 충족해야 신청 물건 달력 조회 |

| DB 반영 | 추후 구현에서도 로컬 스키마까지만 반영. 운영 적용은 별도 승인 후 수동 SQL |
| 보안 | IDOR 방지, 서버 결제 금액 검증, PII 암호화, rate limit 필수 |

### 1.2 기획상 제안하는 기본 정책

다음은 요구사항을 구체화하기 위한 제안이며, 기존 구현 사실이나 확정된 운영 정책이 아니다.

- **기간**: 활성화 시각부터 KST 기준 다음 달 같은 일시까지 1개월. 다음 달에 같은 날짜가 없으면 말일로 보정한다. DB는 UTC로 저장하며 이용 범위는 `[startedAt, paidUntil)`로 정의한다. 30일 고정 상품으로 혼용하지 않는다.
- **가격**: 이용자 결제 총액은 10,000원으로 고정한다. 부가세·영수증 표기 방식은 다날 가맹 설정 시 확정한다.
- **신청 단위**: 주문 하나가 물건 하나만 포함한다. 다른 물건은 별도 주문이며, 같은 신청자·같은 고유번호의 활성 서비스 중복 구매는 차단하고 연장으로 안내한다.
- **신청자 확인 보강**: 타인 이름·전화번호로 신청해 인증된 조회 결과에 타인의 신청이 섞이는 것을 막기 위해, 최초 신청 결제 전에도 다날 본인인증을 수행하는 안을 권장한다. 필수 요구인 조회 시 인증은 별도로 유지한다. 아래 MVP 설계는 이 보강안을 기준으로 한다.
- **연장**: 만료 전 결제하면 기존 `paidUntil`부터 1개월 추가, 만료 후 결제하면 재활성화 시각부터 1개월 시작한다. 중단 구간을 소급 감시했다고 표시하지 않는다.
- **만료 후 조회**: 보관 중인 과거 달력은 본인인증 후 열람할 수 있지만 새 감시는 실행하지 않는다. 실행 로그는 기존 90일 정책을 기본으로 하며, 개인정보·주문 보관기간은 운영 출시 전 별도 확정한다.
- **서비스 범위**: 신청사건 프리체크와 달력 열람을 제공한다. 최신 등기부 유료 발급, 전문 권리분석, 스냅샷·무결성 검증 화면, 회원 전환·회원 데이터 통합은 이번 범위에서 제외한다. 비회원 변동 알림 문자도 별도 확장 사항이며 MVP 필수 문자는 만료·연장 안내다.

## 4. 사용자 흐름과 화면 요구사항

### 4.1 신청

1. `/renewal/monitoring`에서 비회원에게 유료 공지와 회원 요금제, 단건 상품, 신청폼을 함께 표시한다. 기존 `/monitoring` 및 메뉴·매물 상세의 비회원 진입도 이 흐름으로 연결한다.
2. 공지는 “비회원 1건·1개월 10,000원 / 하루 2회 정기 점검 / 자동결제 없음 / 미연장 시 종료 / 현황 조회 시 휴대폰 본인인증 필요”를 명시한다. 프리체크는 신청사건 징후 확인이며 등기 변경 확정이나 PDF 진위 확인을 의미하지 않음을 설명한다.
3. 신청폼에서 이름·전화번호·주소·PDF, 서비스 약관 및 필요한 개인정보 처리 동의를 받는다. 마케팅 동의는 필수 신청 조건에 넣지 않는다.
4. 서버가 PDF에서 주소·고유번호·소유자를 추출한다. 이름은 신청자 이름이며 `ownerName`과 달라도 된다. 임차인도 신청 가능하므로 휴대폰 본인인증을 부동산 소유권 인증으로 해석하지 않는다.
5. 자동 추출 결과와 입력 주소를 대조해 물건을 확인한다. 공백·주소 표기 차이는 정규화하고, 다른 동·호·고유번호 또는 여러 물건이 섞인 PDF는 결제 전에 해결한다.
6. 권장 보강안에 따라 신청자의 다날 휴대폰 본인인증을 수행하고, 서버에서 인증 이름·전화가 신청 입력과 일치하는지 검증한다.
7. 서버가 SSOT의 10,000원·물건 1건·기간 1개월로 주문을 생성하고 다날 결제창을 시작한다. 결제 중 새로고침 시 같은 주문을 복구한다.
8. 서버가 다날 승인 결과를 검증한 후 주문 확정·감시 활성화·유효기간 설정을 원자적으로 처리한다. 완료 화면에 접수 결과, 시작·만료 일시, 현황 조회 링크를 제공한다. 결제 완료 화면만으로 달력 접근권은 부여하지 않는다.

### 4.2 비회원 현황 조회

1. 신청 화면의 “비회원 감시 현황 조회” 또는 문자 링크로 `/renewal/monitoring/guest/status`에 진입한다.
2. 이름·전화번호를 입력한다. 본인인증 전에는 신청 존재 여부·주소·건수·기간을 노출하지 않는다.
3. 다날 휴대폰 본인인증을 진행한다. 서버가 거래 검증, 만료·재사용 여부, 요청 nonce, 브라우저 세션, 인증된 이름·전화 일치를 검사한다.
4. 일치하는 신청만 조회 가능한 제한 세션을 발급한다. 여러 건이면 본인 신청 범위 안에서 물건을 선택하고 한 물건의 달력을 연다. 동일한 물건 고유번호라도 다른 신청자의 이력은 합쳐 보여주지 않는다.
5. 화면은 물건 식별을 위한 최소 주소·활성/만료·이용기간, `MonitoringActivityCalendar`, 연장 버튼만 제공한다. 신청자 PII, 고유번호, 소유자명, PDF 원문, 알림 상세, 스냅샷·무결성·다운로드 기능은 제공하지 않는다.
6. 세션이 만료되면 다시 이름·전화 입력 및 본인인증을 요구한다. 실패·취소·불일치는 상세 원인을 노출하지 않는 공통 안내로 처리한다.

### 4.3 만료 및 연장

- `now >= paidUntil`이면 즉시 비활성으로 판단한다. 만료 작업이 늦어도 다음 프리체크를 실행하지 않는다.
- 만료 처리와 만료 안내 발송 예약을 함께 기록한다. Solapi 문자에는 서비스 만료·연장 금액·안전한 조회 링크를 넣으며 성명·상세 주소·고유번호는 넣지 않는다.
- 문자 링크는 조회 화면으로만 연결한다. 링크·물건 ID·주문 ID가 인증을 대신할 수 없다.
- 본인인증된 소유 신청 범위에서 연장 주문을 생성한다. 최초 신청과 동일하게 금액·승인 상태·중복 처리를 검증하고 성공한 주문마다 1개월만 반영한다.
- 만료 전 연장은 만료 작업과 충돌하지 않도록 최신 `paidUntil`을 잠금/조건부 갱신으로 확인한다. 갱신된 기간에는 이전 기간의 만료 문자를 보내지 않는다.
- 미결제·결제 취소·승인 실패 시 만료 상태를 유지한다. 문자 실패로 유효기간을 늘리거나 감시를 계속하지 않는다.

## 5. 기술 요구사항

### 5.1 요금제 SSOT

- 추후 `lib/pricing-plans.ts`에 비회원 단건 상품의 식별자·총액·통화·물건 수·개월 수·가격 버전을 별도 export로 정의한다. 기존 `PricingPlanKey` 구독 열거형에 단건 상품을 무리하게 추가하지 않는다.
- 회원 요금제 카드·비교표는 기존 `PRICING_PLANS`, `PRICING_COMPARISON`을 그대로 사용한다. 비회원 카드·결제 버튼·서버 주문 생성도 동일 파일의 단건 상품 정의를 참조한다.
- 주문에는 생성 당시 상품/가격 버전과 금액을 스냅샷으로 저장한다. 승인 시 클라이언트 금액 대신 서버 주문의 금액을 기준으로 다날 실제 승인 금액과 대조한다.

### 5.2 다날 어댑터 경계

`lib/danal/`에 아래 역할을 분리한다. 메서드 이름은 내부 계약 제안이며 다날의 실제 API 명세를 확정한 것이 아니다.

| 역할 | 내부 인터페이스 제안 | 검증된 반환값 |
|---|---|---|
| 본인인증 시작 | `IdentityAdapter.startVerification` | 내부 요청 ID, 만료 시각, 인증창 실행 정보 |
| 본인인증 검증 | `IdentityAdapter.verifyResult` | 성공/실패, 검증된 이름·전화, provider 거래 ID |
| 결제 시작 | `PaymentAdapter.createPayment` | 주문에 묶인 결제 실행 정보 |
| 결제 검증/조회 | `PaymentAdapter.verifyPayment`, `getPayment` | 주문 ID, 거래 ID, 금액, 통화, 최종 승인 상태, 승인 시각 |
| 콜백 검증 | `verifyCallback` | 진위·무결성 검증 결과, 재전송 식별자 |
| 결제 취소 | `cancelPayment` | 취소 상태 및 거래 참조; 활성화 불가 결제 복구에 사용 |

- `types`, `identity`, `payment`, `mock`, provider 선택부로 나누고 화면·서비스는 내부 계약만 의존한다. 키와 서명 처리는 서버 전용이다.
- 키 수령 전 목은 성공·인증 불일치·만료·취소·금액 불일치·중복/지연 콜백·승인 후 저장 실패를 재현해야 한다. 임의 `success=true` 파라미터를 인증 결과로 받아들이지 않는다.
- 목도 서버 주문 저장·nonce·세션·멱등성 검사를 거친다. 테스트용 거래와 실거래를 저장 수준에서 구분한다.
- 목은 로컬/격리 테스트에서만 명시적으로 활성화한다. 운영에서 다날 키가 없으면 신청 결제·본인인증을 503으로 차단하고 가짜 성공으로 감시를 열지 않는다.
- 키 수령 후 가맹 상품에 맞는 인증/PG 프로토콜, 서명/암호화, 서버 결과 조회, 반환 URL·콜백 방식, 취소 API를 공식 제공 명세로 확정한다. 키 입력만으로 실결제가 완성된다고 가정하지 않고 실어댑터 구현·가맹 테스트를 별도 완료한다.

### 5.3 데이터 모델 초안

아래는 향후 **로컬 `prisma/schema.prisma` 반영을 위한 논리 설계**다. 이 문서 작성 단계에서는 스키마를 수정하지 않는다.

| 신규 모델 | 주요 필드 | 제약·용도 |
|---|---|---|
| `GuestMonitoring` | `id`, `guestName`, `guestPhone`, `guestIdentityHash`, `address`, `commUniqueNo`, `ownerName`, `status`, `startedAt`, `paidUntil`, `orderId`, `lastCheckedAt`, 프리체크 상태 필드, `createdAt`, `updatedAt`, `draftExpiresAt` | `userId` 없음. 이름·전화 암호화. `orderId`는 최초 서버 주문 식별자로 unique·불변. 초안 상태에서는 기간 nullable, active 상태에서는 필수. `guestIdentityHash`, `(status,paidUntil)`, `(guestIdentityHash,commUniqueNo)` 인덱스 |
| `GuestMonitoringOrder` | `id/orderId`, `guestMonitoringId`, `purpose(initial/renewal)`, `amount`, `currency`, `productVersion`, `status`, `providerTransactionId`, `providerMode`, `paidAt`, `appliedAt`, 적용 기간, `expiresAt`, `idempotencyKey` | 다회 연장 이력 보존. orderId·provider 거래 ID·요청 멱등키 unique. 주문 한 개가 한 물건만 참조 |
| `GuestMonitoringCheckLog` | `id`, `guestMonitoringId`, `checkedAt`, `method`, `result`, `riskLevel`, 최소 `summary` | 기존 `CheckLogItem`과 같은 의미의 DTO로 변환. `(guestMonitoringId,checkedAt)` 인덱스, 90일 정리 |
| `GuestVerificationSession` | opaque 토큰 해시, `purpose`, 요청 nonce/거래 ID, 입력 identity hash, 검증 identity hash, `verifiedAt`, `expiresAt`, `consumedAt/revokedAt` | 인증 요청과 브라우저·용도 결합. 인증 콜백 1회 소비와 조회 세션을 단계로 구분하고 인증 전 권한 없음 |
| `GuestMonitoringMessage` | `guestMonitoringId`, 대상 만료시각, `type`, `status`, `attempts`, `nextAttemptAt`, provider 메시지 ID, `sentAt` | `(guestMonitoringId,type,대상 만료시각)` unique로 중복 예약 방지. 재시도용 outbox |

- `GuestMonitoring.status`: `pending_payment → active → expired`, 미완료 초안은 `abandoned`. 결제 상태는 주문 모델에서 `pending/paid/failed/canceled/refunded` 등으로 별도 관리한다.
- `GuestMonitoringOrder.appliedAt` 및 주문에 기록한 적용 기간으로 동일 결제를 여러 번 반영하지 않는다. 환불 시의 감시 종료·잔여기간 계산 정책은 운영 출시 전 확정하고 자동 환불을 임의로 실행하지 않는다.
- 초기 주문·신청 초안은 트랜잭션으로 생성한다. 결제 대기 초안에는 TTL을 두고 만료 초안·PDF 임시 데이터·미완료 인증을 정리한다.
- 같은 신청자·물건의 중복 활성화는 단순 사전 SELECT만으로 방어하지 않는다. 트랜잭션 잠금/유일 제약 등 동시성 제어를 적용하고, 충돌 결제는 재확인·취소 복구 대상으로 분리한다.
- 기존 `MonitoringCheckLog`는 `MonitoredProperty` FK가 필수이므로 비회원 ID를 넣을 수 없다. 별도 로그 모델을 선택해 기존 회원 관계의 nullable 변경을 피한다.

### 5.4 개인정보 암호화 및 검색

- 실제 암호화 목록 SSOT인 `lib/pii-crypto-tree.ts`에 `GuestMonitoring.guestName`, `guestPhone`을 등록한다. 소유자명·주소도 개인정보 성격이 있으므로 같은 모델의 암호화 대상에 포함하는 안을 기본으로 한다.
- 주문·세션·문자 모델에는 이름·전화 평문을 중복 저장하지 않는다. 관계를 `include/select`하는 경우 필요한 `MODEL_RELATIONS` 매핑을 등록해 nested 암복호화 누락을 방지한다.
- 검색은 정규화한 이름과 국내 전화번호를 모호하지 않게 직렬화한 후 `hashForSearch`로 생성한 `guestIdentityHash`를 사용한다. 전화는 하이픈·국가번호를 일관되게 정규화하고 이름은 공백·유니코드 정규화 규칙을 동일 적용한다.
- 랜덤 IV 암호문을 `where: { guestName, guestPhone }`로 검색하지 않는다. 해시 검색 후에도 다날에서 검증된 이름·전화와 서버 복호화 결과가 정확히 일치해야 한다.
- 암호화 실패·키 누락·복호화 이상 시 인증·등록·조회는 중단한다. 복호화 함수가 암호문을 반환하는 기존 동작을 일치 판정 성공으로 처리하지 않는다.
- 원본 PDF·원문은 기본적으로 추출 직후 폐기한다. 결제 전 필요한 데이터는 브라우저 세션에 묶인 서버 초안에 최소한으로 저장하고 TTL 후 삭제한다. 파싱 결과를 클라이언트가 다시 보내 덮어쓰는 방식은 사용하지 않는다.
- 로그·감사·rate-limit 키·콜백 원문에는 이름·전화·PDF·인증 비밀값을 남기지 않는다. 감사에는 내부 참조 ID와 결과 코드만 기록한다. 개인정보 및 주문의 최종 보관·삭제 정책은 운영 출시 조건으로 확정한다.

### 5.5 IDOR·세션·요청 보안

- 조회 세션은 서버에서 검증 완료한 identity hash·인증 시각·용도를 가진다. 토큰 원문 대신 해시를 저장하고 `HttpOnly`, `Secure`, 적절한 `SameSite` 쿠키를 사용한다. 초기 제안 유효시간은 15분이며 만료·로그아웃 시 폐기한다.
- 모든 조회·주문 조회·연장 요청에서 세션 검증 후 `id + verified identity hash` 조건으로 신청을 찾는다. ID가 추측 불가능하더라도 권한 검사를 생략하지 않는다. 무권한과 없는 물건은 동일한 404 응답을 사용한다.
- 신청 입력 세션, 결제 대기 상태 조회 권한, 인증된 달력 조회 권한을 구분한다. 결제 리턴 URL·주문 ID·문자 링크·서버 파싱 토큰은 달력 열람 권한이 아니다.
- 콜백의 state/nonce·거래 ID·세션·용도를 검증하고 인증 요청은 한 번만 소비한다. 클라이언트 전달 이름·전화·성공 여부를 다날 인증 결과 대신 신뢰하지 않는다.
- 브라우저 쓰기 API는 기존 `validateOrigin` 및 CSRF 방어를 재사용한다. 외부 다날 콜백은 브라우저 Origin 검사 대신 provider 검증·state/nonce를 적용한다. 교차 사이트 반환에도 요청 결합이 유지되도록 쿠키·리다이렉트 동작을 가맹 테스트에서 확인한다.
- 개인정보 응답은 `Cache-Control: no-store`, 공유 캐시 금지. 이름·전화·인증 토큰을 URL/쿼리/분석 이벤트에 넣지 않는다.
- PDF는 기존 10MB·매직바이트 검사 외에 빈 파일, 손상/암호화 PDF, 등기부 아닌 문서, 추출 자원 한도를 검사한다. 스캔·누락·공동소유 모호성은 재업로드/확인 안내로 처리하고 불완전한 입력으로 유료 감시를 시작하지 않는다. 수동 입력만으로 서버 추출 검증을 우회할 수 없다.

### 5.6 결제 검증과 실패 복구

1. 서버가 파싱 초안·신청 본인인증·중복 신청을 검증하고 상품 SSOT에서 주문을 만든다. 클라이언트가 보낸 금액·기간·물건 수는 가격 결정에 사용하지 않는다.
2. 콜백 또는 서버 조회로 다날에서 검증된 주문 ID·가맹 식별·거래 ID·승인 상태·실제 금액·통화가 해당 주문과 일치하는지 검사한다. 금액은 정수 KRW 10,000원이며 실패·취소·미승인·불일치 시 활성화하지 않는다.
3. 주문 확정, 감시 활성화, 적용 기간, `appliedAt`을 DB 트랜잭션으로 반영한다. 같은 주문·거래의 재전송은 기존 결과를 반환한다. 병렬 연장은 물건별 직렬화로 기간 누락·중복을 막는다.
4. PG 승인 후 DB 실패는 `paid but unapplied` 복구 대상으로 남겨 provider 서버 재조회로 재처리한다. 브라우저 성공 페이지 도착을 필수로 삼지 않는다.
5. 결제창 취소·통신 타임아웃은 즉시 재결제를 유도하지 않고 주문 상태를 먼저 확인한다. 최종 활성화가 불가능한 거래는 운영 확인/다날 취소 복구 대상으로 기록하며 성공으로 표시하지 않는다.

### 5.7 감시엔진·달력 재사용

- 회원·비회원 공통 프리체크 입력을 `{ targetId, targetKind, address, commUniqueNo, ownerName, lastSignal }` 형태로 정규화한다. 조회·결과 매핑·재시도 판정은 기존 `lib/tilko-api.ts`, `lib/registry-monitor/` 로직에서 공통화하고 저장/알림만 대상별 어댑터로 분기한다.
- 같은 cron에서 `GuestMonitoring.status=active AND paidUntil > now` 대상을 포함한다. 외부 호출 직전에도 유효기간을 검사하고 만료 작업이 종료 상태를 최신 기간 위에 덮어쓰지 않게 한다.
- 기존 배치 크기 50과 회원 우선 처리가 비회원 전체 누락으로 이어지지 않도록 회원·비회원의 처리량 배분·페이지 순회·미처리 대상을 설계한다. 실패 재시도 대상은 모델 종류까지 포함해 ID 충돌 없이 분리한다.
- 비회원은 `standard` 프리체크만 제공한다. Tilko 미설정·실패 시 정상/이상 없음으로 표시하지 않고 오류로 기록한다. 유료 등기부 발급으로 자동 폴백하지 않는다.
- 상태 갱신과 비회원 실행 로그 저장을 트랜잭션으로 묶고 실패는 관측·재시도한다. 만료·장애·실행 없음은 정상 점검과 구별한다.
- 달력에는 `CheckLogItem` 호환 최소 DTO를 전달한다. 월 범위로 로그를 조회해 재시도 증가가 기존 120건 제한 때문에 이력을 잘라내지 않도록 한다. 로그의 원문·개인정보 포함 summary는 제거/정제한다.
- 현재 달력의 시간 그룹은 브라우저 로컬 기준이므로 이번 기능에서는 KST 날짜·정오/오후 슬롯이 해외 기기에서도 일치하도록 공통 시간 처리만 보완한다. 회원 화면에도 영향을 주므로 회귀 검증한다.

### 5.8 만료·문자·rate limit

- 만료 상태 정리·문자 예약은 정규 감시 cron의 재시도 조기 반환보다 먼저 실행하거나 별도 수명주기 작업으로 분리한다. 만료 알림 지연 목표는 만료 후 1시간 이내로 제안하며, 기존 하루 두 시간대 cron만으로는 달성할 수 없으므로 시간당 작업이 필요하다.
- 실제 감시 종료는 `paidUntil` 조건이 보장한다. 수명주기 cron은 만료 상태와 문자 처리를 보완하며 감시 유효기간을 결정하는 유일한 장치가 아니다.
- 발송 outbox에는 재시도 횟수·다음 시각·실제/목 채널·provider 메시지 ID를 기록한다. 전송 직전에 대상 기간이 여전히 만료인지 재검증한다. 재시도 소진은 운영 알림 대상으로 남긴다.
- provider 응답 유실 시 무조건 재발송하지 않고 메시지 상태 조회/재조정을 우선한다. DB unique만으로 외부 SMS의 정확히 한 번 전송을 보장한다고 주장하지 않는다.
- 기존 DB rate limiter를 사용하고 실패 시 차단한다. 신뢰 가능한 프록시에서 가져온 IP만 사용하며 전달 헤더 전체를 식별자로 신뢰하지 않는다. 운영에서 bypass를 허용하지 않는다.

| 대상 | 초기 제한 제안 | 추가 제한/응답 |
|---|---|---|
| PDF 추출 | IP당 10회/분 | 초안 세션 제한·용량/처리시간 제한, 초과 429 |
| 본인인증 시작 | IP당 5회/10분 | identity hash당 3회/10분 및 일일 비용 한도 |
| 인증 실패·검증 | 세션당 실패 5회/10분 | 요청 TTL·일회성 소비·반복 실패 대기 |
| 신규/연장 주문 | 세션당 5회/분 | 동일 물건 미완료 주문 재사용·멱등키 |
| 달력 조회 | 검증 세션당 30회/분 | IP 제한 병행, 조회 월 범위·보관기간 제한 |
| 다날 서버 콜백 | provider 검증 후 거래 단위 제한 | 중복 정상 ACK와 멱등 처리, 일반 사용자 IP 제한으로 정상 콜백 유실 방지 |

## 9. 운영 DB 반영 경계와 미확정 사항

### 9.1 DB 적용 절차

1. 이번 단계: 이 기획서만 작성한다. 스키마·마이그레이션·DB·배포는 변경하지 않는다.
2. 별도 구현 단계: 로컬 Prisma 모델을 선언하고 격리 DB에서 관계·인덱스·암호화·동시성·삭제를 검증한다. 운영 연결을 이용한 `db push`, `migrate dev/deploy/resolve`를 실행하지 않는다.
3. 운영 변경 준비: 현재 DB 구조와 차이를 확인하고 신규 테이블·인덱스·제약의 수동 SQL, 사전 백업, 적용 검증 및 롤백 절차를 별도 검토 자료로 만든다.
4. 별도 승인 후 수동 SQL로만 적용한다. 이 문서의 작성·검토는 실행 승인이 아니다.
5. 테이블 적용 전 기능은 서버 플래그로 비활성화한다. 승인된 DB 적용·실연동 검증 후 활성화하며, 롤백은 먼저 플래그 OFF와 예약 작업 중단으로 처리한다. 결제/신청 데이터가 생긴 테이블은 임의 삭제하지 않는다.

### 9.2 구현·출시 전 결정할 사항

| 항목 | 현재 기획 기준/결정 필요 내용 |
|---|---|
| 신청 본인인증 | 조회 인증은 확정 필수. 최초 결제 전에도 인증하는 보강안 채택 여부 확정 |
| 한 달 정의 | 달력상 1개월·월말 보정안을 기준으로 약관/결제 화면 동일 표기 확정 |
| 다날 계약 | 휴대폰 본인인증 및 결제 가맹 상품·결제수단·공식 연동 명세·키·허용 URL 확정 |
| 동의·보관·환불 | 필요한 개인정보 처리/전달 고지, 주문 보관·PII 파기, 중도 취소/환불 정책·세금 표기 확정 |

| 감시 장애 | 장애 고지·지원·보상 정책 및 유료 서비스 개방 시 Tilko 운영 가능 상태 확인 |

다음 단계 산출물은 API/상태전이·데이터 모델·위협 시나리오를 포함한 상세 설계서와 수동 DB 변경 계획이다. 실제 기능 구현 및 운영 반영은 이번 요청에 포함되지 않는다.
