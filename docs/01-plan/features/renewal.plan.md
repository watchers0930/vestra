## 1. 기능 개요

회원가입과 플랜 선택·결제를 하나의 renewal 톤 스텝 위저드로 연결한다. 사용자는 `유형 선택 → 소셜 가입 → 가입 정보 → 플랜 선택 → 결제 → 이용 시작`을 하나의 과정으로 인식해야 한다. 사업자 가입 정보 단계에는 관리자 승인 대기를 포함하며, PERSONAL은 승인 없이 세부유형 선택으로 진행한다.

핵심 목표는 다음 세 가지다.

1. 사업자 신청 접수(`pending`)를 인증 완료(`verified`)처럼 보여 주지 않는다. 사업자 3종 모두 서버에서 승인이 확인된 후에만 플랜·결제 단계로 진행한다.
2. renewal 모달에서 OAuth를 거쳐 전체 페이지로 이동해도 타이포그래피·색상·카드·진행 표시가 이어지게 한다. 실화면의 디자인 일관성을 필수 인수 기준으로 삼는다.
3. 플랜과 결제를 가입의 후속 스텝으로 제공한다. 무료 허용 유형은 명시적인 무료 선택으로 마치고, 부동산·기업 신규 계정은 실제 PREMIUM 활성화 전까지 기존 서버 보호 경계를 유지한다.

### 1.1 범위

- 포함: 가입 모달, OAuth 복귀 화면, 개인 세부유형, 사업자 정보·승인 상태, 진행 표시, 플랜·결제 화면의 표현과 연결, 재진입·오류 화면, 관련 기획·설계 정합성.
- 제외: OAuth/관리자 승인 서버 재설계, 신규 결제·주문·무료 완료 API, 구독 상품·가격·기간·체험 정책 변경, DB 스키마/마이그레이션, 비회원 보호 로직, 기존 회원 권한 재분류, 전문가 가입 재설계.
- 이번 단계 산출물은 본 기획서와 관련 설계서 갱신뿐이다. 아래 구현·검증 항목은 후속 작업의 요구사항이다.

## 4. 목표 사용자 흐름

### 4.1 사용자에게 보이는 단계

가입 전·후 같은 진행 표시를 사용한다. PERSONAL/사업자 모두 상위 5단계를 유지하고 3단계 내용만 분기한다. OAuth로 페이지가 바뀌는 것은 허용하되 새 가입 절차가 시작된 것처럼 보이지 않게 한다.

| 표시 순서 | 단계명 | 내용·전이 조건 |
| --- | --- | --- |
| 1 | 회원 유형 | PERSONAL / RENTAL_BIZ / REALESTATE / BUSINESS 선택. 무료 가능·승인 필요·유료 필수 여부 사전 안내 |
| 2 | 소셜 가입 | Google/Naver. 이전 선택 요약과 이후 절차 표시. OAuth 외부 이동 안내 |
| 3 | 가입 정보 | 개인: 세부유형 선택. 사업자: 정보 입력 → 승인 대기 → 승인 완료. pending 동안 현재 단계 유지 |
| 4 | 플랜 선택 | 서버 허용 목록만 표시. 무료 선택이면 결제 생략하고 완료 표시 |
| 5 | 결제 | 선택 플랜·기간·선불 총액 확인, 기존 결제 실행·복구, 서버 확인 후 완료 표시 |

- 개인: `유형 → 소셜 → TENANT/LANDLORD → 무료/PRO → 무료 완료 또는 결제 → 이용 시작`.
- 임대: `유형 → 소셜 → 사업자정보/승인 대기 → verified → 무료/PRO/PREMIUM → 무료 완료 또는 결제 → 이용 시작`.
- 부동산·기업: `유형 → 소셜 → 사업자정보/승인 대기 → verified → PREMIUM → 결제/활성화 → 이용 시작`.
- 결제 완료 또는 무료 선택 뒤 같은 셸 안에서 짧은 완료 안내와 “시작하기”를 제공한다. 유료 완료 안내는 서버 확인 이후에만 표시한다.
- UI 표시 순번과 기존 `WizardStep=1|2|3|4` 및 `/signup/business/step-*`를 구분한다. 5단계 표현을 위해 기존 라우트·서버 stage enum을 변경하지 않는다.

### 4.2 라우트 연결 및 재진입

- 가입 전 1·2단계는 `RenewalSignupModal`이 담당한다. 선택한 유형을 보존하고 소셜 가입을 시작한다.
- `/signup/complete`는 OAuth 복귀·정보 입력 진입점으로 유지한다. 사업자 정보 폼과 대기 화면은 같은 표시 3단계로 연결한다.
- 기존 `step-1`은 계정 진입, `step-2`는 사업자 정보/심사, `step-3`은 플랜, `step-4`는 결제로 유지한다. 직접 링크도 같은 renewal 셸과 기존 단계 가드를 거친다.
- OAuth 실패·취소 시 유형을 가능한 범위에서 복구해 소셜 단계에서 재시도한다. 쿼리·저장소가 모두 없으면 유형 재선택을 제공한다. 기본 사업자 역할을 추정하지 않는다.
- PERSONAL 전용 신규 흐름은 사업자 심사 UI를 생략한다. 사업자 신청 후 실제 role이 PERSONAL로 남은 계정을 순수 개인으로 오인하지 않는다.
- 재개 시 서버 `stage=verify`면 심사 단계, `stage=pay`면 플랜/결제 재개. `complete`라도 신규 무료 허용 계정은 선택적 플랜 화면을 제공할 수 있다. 기존·활성 유료 완료 계정의 홈 복귀 정책은 유지한다.
- 승인 뒤 플랜에 들어갈 때 setup-role을 자동 재호출해 pending으로 되돌리지 않는다. 재신청은 사용자가 수정·제출을 명시한 경우에만 한다.

## 5. 승인·완료 및 플랜 정책

### 5.1 승인 표시 규칙

| 서버 상태 | 표시 | 가능한 행동 | 금지 사항 |
| --- | --- | --- | --- |
| 미조회/조회 실패 | 상태 확인 중 / 확인 실패 | 재조회·재로그인 | verified 추정, 구매 실행, 완료 표시 |
| `none` | 사업자 정보 입력 필요 | 정보 입력·제출 | 인증 완료·플랜 이동 |
| `pending` | 승인 대기 | 상태 다시 확인, 기존 프로필 상태 보기, 나중에 이어하기 | 녹색 인증 체크, “인증 완료”, 인증 단계 완료 처리, 플랜·결제 진행 |
| `rejected` | 승인 반려 | 정보 확인·수정 후 재신청 | 이전 신청의 성공 표시 재사용 |
| `verified` | 사업자 승인 완료 | 서버 허용 플랜으로 이동 | 승인만으로 유료 필수 가입을 최종 완료 처리 |
| PERSONAL 신규 일반 흐름 | 승인 대상 아님 | 세부유형 저장 후 플랜 선택 | 승인 대기 단계 강제 |

판정 권위는 `GET /api/signup/onboarding-status`다. 신청 응답 메시지·JWT 캐시·로컬 isComplete·URL은 승인 근거가 아니다. 승인 대기 화면은 수동 “상태 다시 확인”을 필수 제공하고, 재진입·포커스 복귀 시 서버 상태를 갱신한다. 자동 갱신을 추가한다면 기존 읽기 제한·백오프·언마운트 정리를 지킨다. 심사 소요시간은 근거 없이 약속하지 않는다.

### 5.2 유형별 플랜 및 완료

| 유형 | 승인 필요 | FREE | PRO | PREMIUM | 완료/접근 기준 |
| --- | --- | --- | --- | --- | --- |
| PERSONAL | 아니요 | 허용 | 허용 | 불가 | 역할 설정 후 서버상 기본 접근 가능. 위저드는 세부유형·플랜 선택을 이어서 안내 |
| RENTAL_BIZ | 예 | 허용 | 허용 | 허용 | 플랜 단계는 verified 이후. 무료는 주문 없이 완료, 유료는 적용 확인 |
| REALESTATE | 예 | 불가 | 불가 | 허용 | 신규 대상은 verified 및 실제 PREMIUM active 전까지 2A 보호 앱·감시 제한 유지 |
| BUSINESS | 예 | 불가 | 불가 | 허용 | REALESTATE와 동일 |

- FREE는 유료구독 미보유 상태다. `MemberPlan`에 FREE 추가, 0원 주문, 무료 완료 쓰기 API를 만들지 않는다.
- PRO 월 기준 9,900원/감시 5건, PREMIUM 29,900원/20건 및 기존 기간 할인·허용 상품을 유지한다. 실제 결제는 기존 가격 계산 결과의 기간별 선불 총액이다.
- 부동산·기업은 무료·건너뛰기·체험으로 완료하는 경로를 제공하지 않는다. trialing/grace/paid 주문만으로 PREMIUM active를 대신하지 않는다.
- 서버 `complete`는 보호 앱 접근 판정이고, 위저드의 플랜 선택·무료 선택 완료 표시는 UI 진행 상태다. 개인·임대에 새 유료 의무나 접근 가드를 만들지 않는다.
- `maxStep`은 이동 허용 상한이다. 단계별 완료 체크는 유형 선택, OAuth 성공, 정보 저장/사업자 verified, 명시적 플랜 선택, 결제 서버 확인이라는 실제 사실을 기준으로 표시한다.

## 6. 기술 요구사항

### TR-01. 공통 renewal 표현 계층

- `RenewalSignupModal`을 시각 기준으로 브랜드·진행바·유형 요약·본문 카드·안내·CTA의 공통 표현 계층을 구성한다. 모달/전체 페이지는 호스트 크기만 다르고 같은 표현을 사용한다.
- 인라인 style 중심, 주요 글자 `#1d1d1f`, 보조 `#6e6e73`, 흰 카드, 테두리 `#e5e5e7`, 강조 `#0071e3`, 카드 radius 20px와 내부 둥근 입력·버튼을 기준으로 한다. 미세 여백·폭은 모바일 가독성에 맞춘다.
- `/signup/complete`, `UserTypeSelector`, `BusinessInfoForm`의 구 스타일 및 `VestraLogoMark` 브랜드 영역을 교체 대상으로 한다. 플랜·결제 자식 컴포넌트와 공통 Button이 구 톤을 노출하는지도 실제 화면에서 확인한다.
- 가입 전용 외형 조합을 우선해 기존 구독 관리 화면 소비자에 스타일 회귀가 생기지 않게 한다. 결제 훅과 API는 공통 재사용한다.
- 정상·로딩·오류·신청 접수·대기·반려·완료·Suspense 모두 같은 셸을 사용한다. 기존 3초 임시 완료 화면을 가입 정보 단계 내 접수/대기 전환으로 대체한다.
- 키보드 조작·포커스 표시·모달 포커스 복귀·접근 가능한 라벨·오류 연결을 제공한다. pending은 색상 외에도 문구·아이콘으로 구분하고 진행바에 현재 단계를 전달한다.

### TR-02. OAuth 전후 분리 및 의도 보존

- `markSignupIntent`의 10분 가입 의도 쿠키와 OAuth 신규 가입 허용 검사를 유지한다. 역할은 기존 URL 우선/sessionStorage 폴백으로 복구하고 허용 값만 수용한다.
- 플랜은 원칙적으로 OAuth·사업자 승인 이후 선택한다. 재인증용 플랜·기간 힌트는 기존 `signup/planIntent.ts`를 사용하며 userId·허용 플랜·기간을 검증한다.
- 저장소 접근 실패는 재선택으로 복구한다. 계정 변경·완료 시 힌트를 정리하고 이전 계정 응답이 현재 화면을 덮지 못하게 기존 소유자/요청 세대 가드를 유지한다.
- 사업자번호·개인정보·결제 서명·nonce·callbackContext·imp_uid를 새 힌트 저장소에 넣지 않는다. orderId 복구는 기존 주문 흐름이 전담한다.

### TR-03. 서버 상태와 표시 일치

- `useOnboardingStatus`·`BusinessWizardContext`의 공유 조회를 재사용한다. 셸·인증 화면이 서로 다른 세션 캐시를 승인 근거로 사용하지 않는다.
- setup-role 422는 사업자정보 입력, 200은 개인 설정 성공 또는 사업자 접수다. 400/401/5xx·네트워크 오류는 현재 단계에서 안내하고 성공·홈으로 자동 넘기지 않는다.
- 초기 상태 미확정에는 자식 결제 실행을 막는다. 결제 직후 background refresh와 `updateSession({})`의 기존 동작, 세션 갱신 중 완료 컴포넌트를 유지하는 처리를 보존한다.
- 현재 온보딩 응답은 requestedRole을 노출하지 않는다. 사업자 대기 여부는 서버 `stage=verify`로 식별하고 역할 힌트는 설명용으로만 쓴다. 재로그인 뒤 신청 유형 힌트가 없으면 “사업자 회원”으로 표시하며 새 API 필드를 요구하지 않는다.

### TR-04. 2A 서버 가드 보존 — P0 불변 조건

- `lib/member-subscription/onboarding.ts`의 `resolveOnboardingState`·`requireOnboardingComplete`·`isMonitoringBlockedByOnboarding`, `onboarding-access.ts`, `protected-paths.ts`, `proxy.ts` 및 `lib/auth.ts`의 JWT 플래그 계산을 유지한다.
- `proxy.ts`는 JWT 기반 진입 안내이며 최종 보안 경계가 아니다. DB 기준 서버 권한/온보딩 검사와 직접 API 호출 차단을 제거하거나 클라이언트 단계 검사로 대체하지 않는다.
- agent 고객 생성·물건 추가·감시 재개(`app/api/agent/clients/route.ts`, `[id]/properties/route.ts`, `[id]/toggle-monitoring/route.ts`), 개인 감시·전자계약 감시 및 `monitoring-targets.ts`의 실행 대상 필터를 보존한다.
- 실제 PREMIUM active, 출시 시점, 진짜 grandfather snapshot 판정을 유지한다. 정책 레코드가 있다는 이유만으로 신규 계정을 완료 처리하지 않는다.
- 로그인·가입·인증·결제·복구·현황·고객지원 등 기존 복구 경로를 새 보호 목록에 넣지 않는다. guest 경로 예외도 유지한다.

### TR-05. Release-gated 호환성

- `MEMBER_SUBSCRIPTION_ENABLED` off에서는 통합 구독 스텝을 강제하거나 새 주문 호출을 유발하지 않고 기존 가입·이용 경로를 유지한다. 승인 대기를 승인 완료로 오표시하지 않는 원칙은 항상 적용한다.
- release 판정은 enabled 외에도 정책/가격 버전과 유효 시행일을 검증하는 기존 `memberReleaseConfig` 의미를 따른다. 클라이언트에 별도 상수·서로 다른 출시 판정을 만들지 않는다. 현재 응답의 `isNewSignup`은 출시 판정이 반영된 대상 여부이며 새 API 필드 없이 기존 복귀 정책에 사용한다.
- off/설정 미완비 시 신규·기존 미분류 계정에 새 제한을 추가하지 않는다. 기존 회원·grandfather 및 과거 PRO 권한을 일괄 축소하지 않는다.
- **예외 보존:** 이미 분류된 회원의 만료·한도 enforcement는 flag와 독립적으로 작동한다(`monitoring-targets.ts`). off를 이유로 이 필터를 해제하거나 만료 권한을 복구하지 않는다.
- 이번 문서 작업과 후속 UI 구현에서 환경변수 값·출시일·운영 플래그를 변경하지 않는다.

### TR-06. Guest·결제 계약 무변경

- `lib/guest-monitoring/*`, guest 전용 API·클라이언트·provider 및 `/renewal/monitoring/guest/*` 보호 예외는 변경하지 않는다. 회원 가입에 guest OTP·단건 상품·결제 복구를 혼합하지 않는다.
- `app/api/member-subscription/*`의 요청/응답·오류·소유권·CSRF·멱등·콜백 서명·공급자 검증·활성화 계약을 변경하지 않는다. `setup-role`과 관리자 승인 API 계약도 유지한다.
- `useMemberPricing`·`useMemberSubscription`·`useMemberOrderFlow`를 재사용하고 UI는 서버 상품·권한·주문 상태를 표현한다. 결제 성공 클라이언트 콜백만으로 완료하지 않는다.
- 유료 완료는 서버 주문 `paid && applied`와 온보딩/구독 재확인 후 표시한다. 미확정·취소·실패·재검증은 기존 복구 동작을 제공하며, 결제 이탈을 자동 무료 완료로 바꾸지 않는다.

## 7. 우선순위 및 후속 구현 순서

모든 P0·P1은 이번 기능의 필수 출시 범위다. 보안 보존과 시각 인수 기준 중 어느 하나만 충족해서 출시하지 않는다.

| 우선순위 | 작업 | 완료 기준 |
| --- | --- | --- |
| P0-1 | 기존 보호 경계·release/무료/유료 완료 계약을 회귀 기준으로 고정 | 2A·guest·member 결제 계약 및 기존 회원 동작 보존 |
| P0-2 | 승인 상태·신청 접수·진행바 의미 정리 | pending 인증완료 오표시 0건, verified 전 사업자 플랜/결제 진행 불가 |
| P0-3 | 유형별 플랜·서버 완료 기준 유지 | 기존 허용 목록과 UI 일치, 무료 금지 유형 우회 차단 |
| P1-1 | 공통 renewal 셸 및 complete/세부유형/사업자 폼 전환 | 모달→OAuth 복귀→정보·대기 화면의 실제 화면 일관성 |
| P1-2 | 플랜·결제까지 상위 진행 표시 연결 | 가입 중 구독 선택으로 인식, 무료 생략·유료 완료까지 동일 셸 |
| P1-3 | OAuth/새로고침/승인 후 재개/결제 복구/오류 처리 | 서버 기준 재개, stale 데이터·리다이렉트 루프·중복 주문 없음 |
| P1-4 | 시나리오 회귀 및 모바일·데스크톱 실화면 검수 | 아래 필수 인수 기준과 기존 관련 테스트 통과 |

### 8.2 실화면 일관성 — 필수 인수 게이트

- 데스크톱과 모바일(예: 1440px, 390px/좁은 360px)에서 모달 → 소셜 복귀 → 개인 세부유형 또는 사업자 폼 → 승인 대기/반려/승인 → 플랜 → 결제 → 완료를 연속 확인한다. 가로 넘침·CTA 가림도 점검한다.
- 동일 유형 시나리오의 연속 스크린샷으로 VESTRA 브랜드, 주요/보조 색상, 카드 모서리, 입력·버튼, 진행바·단계명, 폭·여백의 일관성을 비교한다.
- 로딩/Suspense·네트워크 오류·역할 설정 실패·상태 조회 실패·재인증 화면도 검수한다. 클래스명 삭제나 색상 몇 곳 수정만으로 통과 처리하지 않는다.
- pending 화면에서 본문·아이콘·진행바·CTA 모두 대기 상태와 일치해야 한다. 미래 단계가 선택 가능하다는 이유만으로 완료 체크를 표시하지 않는다.
- OAuth 제공자 화면·결제사 외부 UI는 일관성 적용 대상에서 제외하며, 서비스 복귀 즉시 공통 renewal 셸을 복원한다.
